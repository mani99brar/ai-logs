# Task: ruins

## Goal

Build the ruins of §3 as pure, deterministic rules. Each regular island's rubbing sources sit in a ruin that has to be solved before anyone can collect there. There are two short puzzle kinds, a three-symbol sequence and a small navigation puzzle, and reading the clues at the site solves either one. A fresh ruin should take about 20–40 s in total, including the 6 s rubbing. The puzzles must be quick and satisfying for a player who reads the clue, useless to brute-force, and must never leak their answer. `objectives-endgame` wires this into the match room later. This feature only builds and proves the rules.

## Design (settled)

- **One ruin per regular island.** It guards all of that island's sources. The caller supplies each island's real ledger source ids (`source-<island>-<slot>`), and `sources-unlocked` carries exactly those. The match seed deals each ruin a puzzle kind and a puzzle. Generation happens once, at match creation, from the seed and the island list. The state is a plain map from island to {kind, puzzle, sourceIds, solvedBy, lockedUntil per player, open sessions}.
- **The first solve unlocks for everyone.** The first player to solve a ruin unlocks its sources for all players (`sources-unlocked`, once), so contested islands draw rivals together. Every player who solves a ruin gets 40 gold once for that ruin (`gold-awarded`), whether or not it was already unlocked (§11 "once per player per ruin"). Solving again gives nothing.
- **Interaction.** The caller says each tick whether a player is at the ruin (for now: moored at that island's dock). `openRuin` starts a player's session at the ruin and returns only the clue: what the site shows, never the answer. `answerRuin` checks an attempt. A wrong attempt locks that player out of that ruin for 3 s. The lockout is stored per (player, ruin), not per session, so leaving and reopening doesn't clear it. Leaving the ruin (the caller reports it) closes the session, and a session also ends when that player enters a duel.
- **Three-symbol sequence.** The symbol set has six symbols, and the answer is an ordered sequence of three distinct symbols. The clue shows **all six** symbols as carved tablets, each with a relational hint: for example "Tide comes right after Sun", "Storm is not in the sequence", "Moon comes first". Together the hints identify the three symbols and their order uniquely. The clue never reveals which three symbols are in the answer except through the hints. A guesser who ignores the hints faces all 120 ordered triples. A reader deduces the answer in seconds.
- **Navigation.** A 4 × 4 grid with a start cell, a goal cell and 3–5 blocked cells, shown as the clue. The answer is a sequence of compass moves (N, E, S, W) from start to goal that never enters a blocked cell or leaves the grid. Any path of the minimum length is accepted. Generation guarantees the minimum length is 4–6.
- **Hidden information.** The state holds the answers. `clueFor(ruin)` is the only view a client may receive, and it doesn't contain the answer in any encoding.

## Acceptance

Each item names the test that proves it. Tests live in `packages/simulation/src/ruins` unless noted.

1. **Generation:**
   - the same seed and islands give the same puzzles;
   - both kinds occur across seeds;
   - for sequence puzzles, an exhaustive check over all 120 ordered triples shows exactly one satisfies the clue's hints;
   - for navigation puzzles, a breadth-first search confirms a minimum path of length 4–6 exists and the start and goal are open;
   - both checks use **evaluators written in the test file**, independent of the generator's own helpers, so a shared bug can't pass both;
   - property test over 500 seeds.
2. **Clues don't leak:** a test serialises every `clueFor` result over 500 seeds and shows that the answer can't be read from it without the reasoning. For sequences: the display order of the tablets never equals the answer order more often than chance allows (bounded frequency). For navigation: the clue is exactly the grid.
3. **Solving:**
   - a correct answer solves; the first solve emits `sources-unlocked` with that island's source ids, once;
   - every solving player gets one `gold-awarded` of 40 per ruin; a repeat solve gives nothing;
   - a wrong answer locks that player out for 3 s and doesn't affect others;
   - attempts during the lockout, without an open session, after leaving, or while in a duel are refused;
   - repeated and stale requests return the same state.
   Scripted tests for each.
4. **Timing target:** a scripted "reading player" (it answers from the clue's hints) solves each puzzle kind within a few ticks of opening. The **best guesser that ignores the hints** (it may use everything else visible, such as the six tablet symbols) needs at least 100 s on average, and at least 20 s at the 10th percentile, on sequence puzzles over 500 seeds. For navigation, a guesser that enumerates move strings shortest-first gets the same bounds. Both use the lockout constant, not literals. A test also shows that leaving and reopening doesn't clear a lockout.
5. **Determinism:** the state is plain integer data, `hashState` covers it, and a seeded random session (open, wrong and right answers, leave, duel) replays to the same hash.
6. **Content:** the constants (lockout 3 s, gold 40, the symbol set, grid size, path-length bounds, blocked-cell bounds) live in `@pirate-sea-race/content/ruins` with a zod validator. A content test refuses a negative lockout and a path-length range the grid can't hold.
7. **Docs:** `docs/ruins.md`, about a page: the puzzle kinds, the clue formats, the state, the operations and events, and how the caller maps them onto the ledger (`unlockSource` per unlocked source; gold through a later ledger operation).
8. `npm ci` then `npm run typecheck`, `npm run test:unit`, `npm run test:integration` and `npm run build` pass from a clean checkout, and the purity test covers the new directories.

# Decisions: ruins-core

From the overnight session of 2026-09-24/25. The operator is asleep and asked the assistant to decide, record each decision, and use the workflow for the code.

## Decisions

- The ruins are built as pure rules first, like the claim, ledger and encounters code, in parallel with the online work. `objectives-endgame` wires them into the match room.
- There is one ruin per regular island, guarding all of that island's sources (the slice has 2 per island).
- The first solve unlocks the island for everyone, and each solver gets 40 gold once. Contested islands then draw rivals together, which feeds encounters, and nobody can farm the gold.
- Two puzzle kinds, matching §3:
  - A three-symbol sequence: all six symbols appear as tablets with relational hints, so a guesser faces all 120 options while a reader solves in seconds (3 s lockout per player and ruin).
  - A 4 × 4 navigation grid with a minimum path of 4–6 moves; any minimum path is accepted.
- Until walking on islands exists, "at the ruin" means moored at that island's dock, as the caller reports it.
- Gold from ruins is new gold. The ledger's `goldIssued` rule needs a grant operation for it, added when the ruins are wired in. This feature only emits `gold-awarded`.

- Corrected after design challenge attempt 1 (its alternative, adopted):
  - Three answer tablets would have given away the symbols, so a guess would take 15 s. Now all six are shown with relational hints.
  - The lockout is per player and ruin, so leaving doesn't reset it.
  - The caller passes the real source ids.
  - The tests use their own independent evaluators, and the brute-force bound uses the best non-reading guesser.

## Assumptions

- The exact clue formats and wording are the worker's choice, within the stated guarantees (a unique deduction, no leak).
