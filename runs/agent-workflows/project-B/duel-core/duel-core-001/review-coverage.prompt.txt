# Decisions: duel-core

From the operator session of 2026-09-24 (slice planning after the skeleton merged into `main`), revised after design challenge attempt 1 of duel-core-001 by the assistant under the operator's standing instruction to finish the run.

## Decisions

- Scope is the pure duel simulation only (slice 1 of the plan). Networking, the arena client and the duel room are the next feature, `duel-online`, which builds against this feature's API from `main`. The API therefore has to be usable without changes: a step function, a snapshot that is plain data, and a pure replay function.
- One lane (`duel`). Duel rules and move data are too coupled to split, and a split lane would fail its isolated typecheck against the other's types.
- Only the Duelist kit. Fruit kits (§9) come with the content slice; the Duelist's two specials are the advancing thrust and the counter slash.
- Haki abilities (§10: Armament, Observation parry, Resolve finisher) and the Haki meter are deferred. The spike's exit (§18: guard, punish, throw, simultaneous hit, reconnect) doesn't need them, and they add balance work before the core is proven.
- Units: integer sub-pixels, 16 sub-pixels per arena pixel. Positions, velocities, gravity and hitboxes are integers; hitboxes and hurtboxes are axis-aligned rectangles relative to the fighter's origin and facing.
- The code lives in new directories behind subpath exports (`@pirate-sea-race/simulation/duel`, `@pirate-sea-race/content/moves`), so this feature edits no existing file. `world-sea` runs at the same time on the rest of the repository, and the two branches must merge without conflicts.
- No browser check: nothing is rendered. The policy's checks are typecheck, unit, integration (unchanged, to prove nothing broke) and build.
- Proving the build output (challenge P1): `scripts/smoke-build.ts` hard-codes the existing exports and `scripts/` is not this lane's (the policy can't change without a new run, and `world-sea` owns `scripts/`). So each of the two packages proves its own new subpath with a `postbuild` script that imports it from `dist/` without the source condition. Adding the two subpaths to `smoke-build.ts` is left for the merge or a later feature.
- The replay runner is a pure `replayDuel` in `packages/simulation/src/duel`, with the log's zod schema in `packages/content/src/moves` (challenge P2). `packages/test-tools` would need a new dependency on `simulation`, and so a lockfile change, and the lockfile belongs to `world-sea` in this parallel pair. `duel-online` can wrap `replayDuel` in `test-tools` later. This departs from §17's "test-tools: replay runner" for now.
- Simplified collision data (challenge's simpler alternative): one hitbox per move for its whole active phase and one hurtbox per stance. Per-frame timelines wait until playtests need them.
- Same-frame rules the spec leaves open, decided here: detect everything against start-of-frame state and apply together; throw against throw breaks both with no damage; an active strike beats a throw in startup or active; stamina and guard breaks use start-of-frame stamina. A mirrored-players symmetry test guards order independence.
- The duel input carries held directions as separate left/right/up/down bits, so the step resolves both-horizontal to neutral (§8) and `duel-online`'s adapter passes keys through unchanged.
- The four §8 baseline moves take their timings from `baselineFrameBudgets` and reuse `moveTimingSchema`, and the duel state records `MOVESET_VERSION` so a snapshot is never replayed against other move data.

## Assumptions

- The arena is one plane with two walls and a floor; its width is content data. There's no stage hazard and no ring-out.
- A duel input per player per frame is one bit field: held directions (left, right, up, down) and buttons (light, heavy, special one, special two, dash), as §8 maps keys. Keyboard mapping is client work.
- Frame data for moves outside §8's table (launcher, anti-air, the two specials) is the worker's choice within §7's ranges, documented in the move data.
- `hashState` from `packages/simulation` is reused for duel state, which also holds the duel's own frame counter and generator state if it needs one.
- The duel starts both fighters at fixed positions, facing each other, with full health and stamina, as §6 requires ("no free opening hit").

## Deferred

- Haki meter and abilities (§10), fruit kits (§9), focus scrolls.
- Networking, prediction and reconciliation, the input delay policy, reconnect: `duel-online`.
- Rendering, animation, the duel HUD and control remapping: `duel-online`.
- Hosting the duel inside `MatchRoom`, reservations, transitions and theft: `encounters-theft`.
