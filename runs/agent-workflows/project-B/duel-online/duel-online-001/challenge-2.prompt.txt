# Task: duel

## Goal

Build the combat spike of §18 stage 1: two browsers fight a 1v1 duel online with the approved duel simulation, through a standalone duel room, with §15's server-authoritative prediction and rollback, and a harness that measures it under simulated latency, jitter and loss. A practice mode against a dummy lets one player try the controls. The spike's exit, "guard, punish, throw, simultaneous hit and reconnect cases are credible online", is judged by the operator's playtest after this run; this task delivers everything that playtest and the automated checks need.

## Context

- Read `docs/spec.md` §6 ("Reservation and transition": countdown, readiness), §7, §8 (controls), §12 (disconnect in a duel), §13 (duel HUD and result), §15 (all of it) and §19 ("Network and performance targets", "Combat determinism").
- Read `docs/duel.md` (the duel simulation: `stepDuel`, snapshots, `restoreDuel`, `replayDuel`, the throw chord window, moveset versioning) and `docs/architecture.md` (rooms, admission, input gate, visibility, tests).
- The duel API is `@pirate-sea-race/simulation/duel` and `@pirate-sea-race/content/moves`. Use it as it is; see Constraints for the one exception.
- The verifier runs `npm ci`, then `npm run typecheck`, `npm run test:unit`, `npm run test:integration`, `npm run build` (ending with `scripts/smoke-build.ts`) and `npx --no-install playwright test --config=tests/e2e/playwright.config.ts`. Playwright's Chromium for `@playwright/test` 1.63.0 is installed and shared read-only; never run `playwright install`.

## Constraints

- Keep the duel rules untouched: no change to what `stepDuel` computes or to the move data. You may add to the duel API (for example, helpers the netcode needs), with unit tests, but any existing test in `packages/simulation/src/duel` or `packages/content/src/moves` must pass unchanged.
- The server is the only authority on hits, health and the result (§15); clients send frame-tagged inputs only, validated with zod in `packages/protocol` like world input, with the same size, rate, sequence and future-frame limits. Bump `PROTOCOL_VERSION`.
- Duel rooms use the same three-layer private admission as matches (code or one-time create token; `onAuth` before any seat; the room's own check), and hold exactly two players, or one in practice mode.
- Keep the sea feature working: all its checks and its four browser scenarios stay green.
- Use existing tooling (Colyseus messages and reconnection, Phaser, zod, Vitest, Playwright). No new runtime dependency unless an existing one cannot do the job; pin exactly and justify it in `docs/architecture.md`.
- Tests must drive input the way players do: keys held through actions, taps shorter than a frame window, the throw chord pressed with ordinary rollover.
- Out of scope: embedding duels in `MatchRoom`, encounters, reservations from the sea, theft, fruit kits, Haki, art and sound.

## Acceptance

- **Duel room** (`apps/server`): a standalone Colyseus room per duel, created by one player with a code the other joins (and a practice variant with a server-side dummy whose behaviour can be switched between idle and guarding). A 3-second countdown starts once both are connected (§6). The room steps `stepDuel` at 60 Hz, applies each player's input for its frame, repeats a player's last input for at most 250 ms and then uses neutral, and never lets late input rewrite a completed frame (§15). It ends the duel with the step's result, which it announces to both.
- **Wire protocol** (see `decisions.md`): clients send **batched, redundant input messages**, each carrying the inputs of the last few frames (for example up to 4, within the 128-byte cap), at no more than 30 messages a second. The server takes each frame's input from the first message that carries it. The existing input gate's limits stay exactly as they are and see zero rate-limited drops in the harness. The server sends one **frame bundle** per cadence (for example every 3 frames) with the inputs it actually applied for each frame since the last bundle, substitutions included, and a full snapshot in every second bundle (the state hash otherwise).
- **Input delay** (§15): the shared input delay is 3 to 8 frames, chosen once per duel from round-trip and jitter measured during the countdown, applied to both players, and shown in the HUD.
- **Rollback core, written once**: a pure module at the subpath `@pirate-sea-race/simulation/netcode` (purity rules apply: the caller supplies time, with no timers and no DOM), unit-tested and loaded from `dist` by `scripts/smoke-build.ts`. It keeps about two seconds of serializable duel states and inputs, predicts both fighters with `stepDuel` (the opponent's last confirmed input repeated), and applies each frame bundle. When a confirmed input differs from what it predicted, it restores the last confirmed state and replays: confirmed frames use the inputs **the server applied** (never the client's own record of what it sent), and later frames use the local and predicted inputs. It counts each correction. The browser client and the headless duel client in `packages/test-tools` both use this module, so the harness proves the code the operator plays.
- **Client clock**: the client's duel frame tracks the server's from the bundles and the measured round-trip: a fixed-step accumulator, a catch-up cap per tick, and a resync from the latest snapshot after a stall or a hidden tab. It does not rely on the display's frame rate. Events that could repeat after a correction (hits, KO) carry stable ids so the view doesn't show them twice.
- **Reconnect** (§12): a player who drops mid-duel gets neutral input after the held-input timeout, can rejoin the same duel within 10 seconds and continue from the authoritative state, and forfeits after 10 seconds absent. An integration test covers rejoining and forfeiting.
- **Arena client**: a Phaser arena scene draws both fighters, their stance and current move with placeholder shapes, with a developer toggle that shows hitboxes and hurtboxes. A duel HUD (§13) shows both health bars, stamina, the round clock, the connection line (round-trip, input delay, corrections) and the result screen. The landing page offers "Create duel", "Join duel" (by code) and "Practice". Controls follow §8: WASD or the arrow keys to move, J light, K heavy, U special one, I special two, Shift dash, and J with K together to throw.
- **Impairment harness** (`packages/test-tools`): a WebSocket proxy that adds latency, jitter and loss the way TCP does. Messages in one direction are never reordered (jitter only delays), and loss becomes a head-of-line stall of about an RTO (for example 200 ms) for everything queued behind it. The random source is seeded. Also a wrapper that runs `replayDuel` on a recorded log.
- **Harness test**: an integration test runs a scripted duel between two headless duel clients through the harness, at no impairment and at the §19 scenario of 80 ms round-trip, 20 ms jitter and 1 % loss. It shows:
  - **zero desyncs**: every client hashes its *own* simulated state at every snapshot frame, before any restore, and compares it with the server's hash;
  - zero rate-limited input drops;
  - corrections within a documented threshold.

  It records the correction and substitution counts as test output.
- **Dev latency setting**: a dev-only setting (for example a URL parameter read only when `import.meta.env.DEV`) that delays the client's socket in both directions, round-trip probes included, and adds jitter, so the operator can playtest §19's latencies locally. It is absent from the production build. Document it in the README.
- **Browser scenarios** (the six in `policy.json`): the four sea scenarios still pass, plus `duel-practice` and `duel-online` as described there.
  - `duel-online` reaches the result screen in both views, so it sets its own test timeout above the 60 s round plus the 3 s countdown (the rules stay as they are).
  - `duel-practice` presses J and K the way rollover does, back to back with no deliberate wait. Integration or unit tests cover exact gaps of 1 and 2 frames, where frame timing is deterministic.
- `docs/duel.md` gains the netcode protocol (messages, rates, the rollback loop, input delay selection, reconnect), and `docs/architecture.md` gains the duel room and harness. Both stay concise.
- `npm ci` then each of the five policy checks passes from a clean checkout.

# Decisions: duel-online

From the operator's grill session of 2026-09-24, after slices 1 and 2 (duel core, sea) merged into `main`.

## Decisions

- Duel entry: a standalone Colyseus duel room joined by its own code, plus a practice mode against a server-side dummy. It hosts the same duel simulation object that `MatchRoom` will embed in `encounters-theft` (§14). This keeps the spike isolated from the sea and from reservations, transitions and theft.
- Netcode: §15's server-authoritative prediction and rollback. Clients predict with the shared `stepDuel`; the server sends checkpoints and input acknowledgements, and a mismatch restores the checkpoint and replays. The shared input delay is 3–8 frames, chosen per duel from measured latency. This is the part the spike exists to prove; a plain input-delay model was rejected because its findings would not carry over.
- Wire protocol, revised after design challenge attempt 1 (P1: one input message per frame would hit the unchanged 60-per-second gate cap and drop real presses). Clients send batched, redundant inputs (the last few frames per message, at most 30 messages a second). The server sends one frame bundle per cadence with the inputs it applied, substitutions included, plus a snapshot every second bundle or a hash otherwise. The client rolls back as soon as a confirmed input differs from its prediction; the snapshot is the authority and the desync detector. This is one message type in each direction and one code path to prove.
- The rollback core is a single pure module, `@pirate-sea-race/simulation/netcode`, used by both the browser and the headless harness client (challenge P1: otherwise the harness would prove a reimplementation, not the client the operator plays). It follows the purity rules, with the caller supplying time.
- Evidence must not be trivial: clients compare the hash of their own simulated state at snapshot frames, before restoring anything, and the harness proxy never reorders and turns loss into a head-of-line stall.
- One fullstack lane (`duel`). A lane can't compile against another lane's new types, and the arena, the netcode and the room share new protocol types.
- The spike's exit (§18) is judged by the operator's playtest after the run: guard, punish, throw, simultaneous hit and reconnect must feel credible at §19's latencies. The run delivers the automated evidence (hash agreement and bounded corrections through the impairment harness) and the dev latency setting the playtest needs.
- The sea's density problem (224×208 tiles, 99.2% sea, 10-tile sight radius) is deferred to `encounters-theft`, where sight, speed and travel times can be tuned against real encounters.
- Tests drive input like players do (held keys, short taps, the throw chord with rollover), after world-sea's docking bug passed every check with idealised input.

## Assumptions

- Checkpoints and inputs travel as Colyseus messages over the existing reliable WebSocket; the room's synced Schema state is not used for the duel's frame data. Head-of-line stalls from loss are exactly what the harness measures.
- The duel room reuses the input gate's limits (size, rate, sequence, future frames) with a duel input schema.
- `packages/test-tools` may now depend on `@pirate-sea-race/simulation` (for the replay wrapper and the headless duel client), because this feature owns the lockfile.
- Rates the worker chooses and documents: checkpoint frequency (for example every 6 frames), the input forwarding cadence, and the correction threshold used in the harness test.
- The dummy's behaviour (idle or guarding) is a practice-mode option, not an AI.

## Deferred

- Embedding duels in `MatchRoom`, grapples and challenges, reservations and the 3-second transition from the sea, theft and respawn: `encounters-theft`.
- Haki abilities, fruit kits, art, animation and sound.
- Duel spectating (§6 defers it).
- Tuning the input-delay policy after the playtest (§15 "Tune this policy in the spike"): a follow-up if the playtest asks for it.
