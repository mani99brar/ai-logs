# Task: duel

## Goal

Fix what the review of run duel-core-001 found in the duel simulation on this branch: a keyboard player must be able to throw, a strike that misses must not cancel a throw, and the rollback contract must be airtight (slot-neutral separation, a moveset version derived from the data, fully validated snapshots). Everything else about the duel stays as it is.

## Context

- This branch contains duel-core-001's result. `features/duel-core/duel-task.md` and `features/duel-core/decisions.md` still define the duel, and all of it still applies. Read `docs/duel.md` first, then `packages/simulation/src/duel/step.ts`, `snapshot.ts`, `replay.ts` and `packages/content/src/moves`.
- The verifier runs `npm ci`, then `npm run typecheck`, `npm run test:unit`, `npm run test:integration` and `npm run build`; the packages' `postbuild` self-checks must keep passing.
- The `world-sea` feature may still be running on the rest of the repository. Stay inside your owned paths.

Findings to fix (P1 are required):

1. (P1) Throw input. `step.ts` starts a jab as soon as `light` is buffered alone (around line 369), so pressing J and then K one or two frames later gives a jab, never a throw. Keyboard rollover rarely lands both keys on the same 60 Hz frame. Add a short throw chord window (one or two frames, a named rule constant): a light or heavy that a free fighter started converts into a throw when its partner button arrives within the window, before the move's first active frame. Prefer this conversion because it keeps every §8 startup (the jab stays 7 frames from the press). Delaying a lone light or heavy instead is acceptable only if the task's frame-advantage and punish tests still hold and `docs/duel.md` states the added delay.
2. (P1) Whiff beats throw. The throw-cancel check (around lines 73–74) uses `strikeActive`, which is true "whether or not it reaches". A jab facing away or out of range therefore cancels a connecting throw. Cancel a throw only when the opponent's strike actually hits or is blocked on that frame.
3. (P2) `separate()` breaks an exact tie (equal x and equal facing) by slot, so a mirrored run can differ. Break it without reference to the slot (for example by previous x or velocity), and cover it with the symmetry test.
4. (P2) `MOVESET_VERSION` is the hand-written string `"duelist-1"`. Derive the version that snapshots and replays carry from the move data itself (for example `hashState` of the moveset), so changed data can never keep an old version.
5. (P2) `restoreDuel` checks only the top-level shape. Validate every field of a restored state (types, integer ranges, known move ids, both fighters) before it is stepped, and refuse anything else.
6. (P2) `DuelMove` and `DuelMoveset` are hand-written beside their zod schemas and joined with `as` casts. Derive the types with `z.infer` (or prove equality at the type level). Replace the three `as unknown as Pair<...>` casts in `step.ts` with a typed helper.
7. (P2) The symmetry test doesn't assert that its scripted trade happens. Assert that the same-frame jab trade gives both fighters a hit event.
8. (P2) `docs/duel.md` doesn't mention the counter slash's strike invulnerability or the throw chord window. Add both.

Found by the official reviewers of duel-core-001 (general and coverage):

9. (P2) A guard break sets stamina to 30 (`step.ts`, around line 289: `Math.min(maxStamina, guardBreakStaminaRestore)`). §7 says a guard break "restores 30 stamina": add 30, capped at the maximum.
10. (P2) The moveset validator's "no free opening hit" check (`packages/content/src/moves/schema.ts`, around lines 923–927) ignores a move's `advance`, so an advancing special could reach an opponent at the start distance. Include the distance a move travels through startup and active frames.
11. (P2) The guard-break test (`duel.test.ts`, around line 327) probes only the cost threshold from a fresh state. Also cover a guard break after regeneration timing matters, and the stamina restored by a break.

## Decisions

- This is a follow-up feature on top of duel-core-001's result, not a new run of `duel-core`: the lane changes only what `duel-task.md` lists, and reviewers review this diff.
- Throw input: a light or heavy started by a free fighter converts into a throw when the other button arrives within a short chord window (one or two frames, a named rule constant), so a keyboard J+K with ordinary rollover becomes a throw. - A guard break adds 30 stamina, capped at the maximum: the plain reading of §7's "restores 30 stamina" (duel-core-001 set it to 30).
- The moveset version is derived from the move data (a hash), not written by hand.
- One lane (`duel`) with the same owned paths as `duel-core`, so it can still run beside `world-sea`.

- The chord window applies only to a fighter that can act; the existing 4-frame buffer still covers inputs made during recovery.
