# Decisions: skeleton

From the grill session of 2026-09-24 with the operator (question 1 in md-manager's session, questions 2–5 in the workflow-grill session).

## Decisions

- Scope: a walking skeleton. It covers the §17 layout and toolchain plus one thin end-to-end path, where browsers join a private match and see ships the server moves. There are no combat, islands or rubbings. A tooling-only scaffold and the §18 stage 1 combat spike were rejected.
- Numbers in `packages/simulation` are integers (fixed-point): every position, velocity and speed in the state is an integer, and the step function never calls `Math.sin`, `Math.cos`, `Math.sqrt` or other floating-point transcendental functions. Diagonal movement is normalised with an integer approximation or lookup table. Consequence: `hashState` is engine-independent, so the combat spike can run the same step in browsers without changing the state shape.
- The sea is a map grid laid out like coordinates: a bounded rectangle with the origin (0,0) at the top-left, x increasing right and y increasing down. It is made of tiles, each split into a fixed integer number of sub-units. Ships move continuously in sub-units, not tile by tile, and are clamped to the map bounds. Positions can be read as a tile plus an offset. Tile size, map size in tiles and ship speed are typed data in `packages/content`.
- State sync: `apps/server` holds a Colyseus Schema state that mirrors the plain simulation state after each world step, and the client decodes it with `@colyseus/sdk`. `packages/protocol` defines client→server messages, their validation and the protocol version, not the synced state shape. Consequence: delta patches and the patch rate come from Colyseus, and §16's per-player hidden information can later use Colyseus StateView.
- Use existing tooling rather than rebuilding it: when a maintained library or a framework feature already solves a problem, use it (for example Colyseus matchmaking, `filterBy`, Schema and the simulation interval; a schema library for protocol validation; Vitest projects; Playwright `webServer`). Every workspace keeps a conventional, consistent layout (`src/`, tests next to or under it, its own `package.json` and `tsconfig.json` extending `tsconfig.base.json`). Consequence: reviewers may flag hand-rolled replacements for standard tools.
- Player count: a private match holds 1 to 8 players and is marked custom. A ship spawns and can sail as soon as its player joins, with no lobby phase, ready check, start button or match timer. A ninth join is refused with a message the client shows. This intentionally differs from §2's "two to eight" for private tests; that minimum arrives with match phases.
- Private match codes: the landing page has a "Create match" button and a "Join" field. Create makes a room with a server-generated six-character code (uppercase letters and digits, for example `K7Q2MX`), shown in the HUD. Join accepts only an existing code (case-insensitive) and shows "No match with that code" otherwise. Rooms are found with Colyseus `filterBy(['code'])`.
- Scenario `join-private-match`: the browser creates a match from the landing page, and the HUD shows its code, the protocol version, one player and "connected". This satisfies the scenario's "enters a private match code". Scenario `two-ships-sync`: the first context creates the match, and the second reads the code from the first context's HUD and joins with it.

## Assumptions

- The pure packages may depend on plain TypeScript libraries (for example a schema validation library) as long as those libraries do not bring in Phaser, Colyseus, DOM APIs, timers, wall-clock time or `Math.random`. The purity unit test checks the packages' own source imports.
- The server runs the 60 Hz match clock with Colyseus's simulation interval, runs world logic (ship movement) on every third step, and patches clients at 20 Hz or less. The client interpolates between patches for drawing. The DOM readout of authoritative positions shows the latest decoded server values, not interpolated ones.
- Clients tag each input with their estimate of the server frame, based on the last patched frame. The server drops inputs whose sequence is not strictly greater than the last accepted one from that client, and inputs whose frame is more than a fixed window (at most 30 frames) ahead of its current frame. It caps message size and per-client message rate, and drops anything over the caps without crashing.
- Movement axes are integers or numbers in [-1, 1], and out-of-range values are rejected (the worker may choose clamping instead, but must test whichever it chooses). Buttons are a bit field. Only movement is used in this feature.
- Spawn positions come from a fixed list of eight spawn slots in `packages/content`, and the seeded generator in the match state assigns them. Two ships never share a slot.
- The protocol version is a single constant exported by `packages/protocol`. The client sends it in its join options, and the server refuses a mismatched version in `onAuth` or `onJoin` with a readable error that the client shows.
- When a client leaves, its ship is removed. There is no reconnection.
- Playwright's `webServer` entries start the server on 2593 and the web client on 5393 without depending on a prior `npm run build`: they either run the dev servers or build what they need themselves.
- The shared frame-budget table and rules presets live in `packages/content` as typed data with a validator. They are not used by the simulation yet.
- A package that the policy lets a worker pin to its previous major is recorded as an open assumption in the worker's result and in `docs/architecture.md`.
