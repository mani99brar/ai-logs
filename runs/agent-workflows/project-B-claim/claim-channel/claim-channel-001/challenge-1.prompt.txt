# Task: claim

## Goal

Build the treasure-claim rules of §5 as pure, deterministic code: who may claim, the ten-second channel, everything that interrupts or resets it, and the ordering rules that make simultaneous events and the match deadline come out the same way every time. Later features wire it into the match room. This one only builds and proves the rules.

## Context

- Read `docs/architecture.md`, the existing pure packages (`packages/simulation`: integer state, `hashState`; `packages/content`: rules and validators) and `tests/unit/purity.test.ts`.

- Two other features run at the same time: `duel-online` (most of the repository) and `objectives-ledger` (`packages/simulation/src/objectives`, `packages/content/src/objectives`), which owns rubbing inventories. Stay inside your owned paths.

## Constraints

- Owned paths only: `packages/simulation/src/claim`, `packages/content/src/claim`, `docs/claim.md`, and `packages/simulation/package.json` and `packages/content/package.json` **only to add one subpath export each** (`@pirate-sea-race/simulation/claim`, `@pirate-sea-race/content/claim`, following the existing pattern with the `@pirate-sea-race/source` condition first). Do not change their `postbuild` scripts or dependencies, any existing source file, barrel, tsconfig or root file.
- Do not depend on the ledger: whether a player holds all four types is an input the caller supplies each tick (a boolean per player), so the two features stay independent.
- Pure and integer: no Phaser, Colyseus, DOM, timers, wall-clock time, `Math.random` or floating-point transcendental functions. Time is the world tick (20 per second) supplied by the caller. Durations are named content constants (for example the 10-second channel is 200 world ticks).
- The claim step is a function of (config, claim state, a per-tick world snapshot of the relevant players) that returns a new state and the tick's events. It never mutates its input.
- Out of scope: networking, rooms, rendering, the final-island choice and navigation, encounters themselves (the caller reports accepted encounter reservations), rubbings.

## Acceptance

- **Eligibility** (§5): a player may claim while holding all four types, inside the treasure circle (a content-defined radius around the final island's claim point), stopped, not protected and not reserved for a duel. Starting a claim ends that player's protection first (§6).
- **The channel**: holding interact for 10 seconds completes the claim. Only one channel is active at a time; a second eligible player must wait. Moving, losing eligibility (a lost type), disconnecting or entering a duel resets progress to zero.
- **Completion**: completing commits the winner once and freezes all match outcomes. Inputs arriving after a resolved win cannot cancel it.
- **Same-tick ordering** (§5): each tick processes accepted encounter reservations before advancing claim channels. When several players begin claiming on the same tick, the closest to the claim point wins, then the lowest stable player id. The order players appear in the input never matters.
- **Deadline** (§2): a claim that completes on the deadline tick is processed before the timeout. A match that reaches the deadline without a winner ends with no winner. A duel still running at the deadline is reported as ending without theft (an event for the caller).
- **Tests**:
  - scripted unit tests for every rule above;
  - a symmetry test showing that reordering or relabelling the players gives the same outcome under the ordering rules;
  - seeded random tick sequences showing that at most one winner is ever committed and that the state hashes identically on replay.
- `docs/claim.md` (about a page): the state, the order of operations within a tick, and the events.
- `npm ci` then `npm run typecheck`, `npm run test:unit`, `npm run test:integration` and `npm run build` pass from a clean checkout, and the purity test covers the new directories.
