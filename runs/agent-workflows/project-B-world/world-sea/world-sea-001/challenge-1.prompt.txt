# Task: world

## Goal

Turn the skeleton's empty rectangle into the §3 sea: an authored tile map with four small islands, shoals and docks, ships that sail with acceleration, braking and turning and cannot cross land or shoals, docking at island docks, and a sight radius that the server enforces, so no client receives ships it cannot see (§16). Browsers show the map, their own view of nearby ships and a fogged minimap.

## Context

- Read `docs/spec.md` §3 (sea and islands: movement, visibility, travel-time targets), §2 ("Spawn fairness"), §16 ("Hidden information") and §17 ("Content definitions": tile-editor maps, validators). Read `docs/architecture.md` and the skeleton code it maps, especially `packages/simulation` (integer state, `step`, `hashState`), `packages/content/src/sea.ts`, `apps/server/src/MatchRoom.ts` and `schema.ts`, and `apps/web`.
- The verifier runs `npm ci`, then `npm run typecheck`, `npm run test:unit`, `npm run test:integration`, `npm run build` (ending with `scripts/smoke-build.ts`) and `npx --no-install playwright test --config=tests/e2e/playwright.config.ts`. Playwright's Chromium for `@playwright/test` 1.63.0 is installed and shared read-only; never run `playwright install`.
- Another feature (`duel-core`) runs at the same time and adds `packages/simulation/src/duel`, `packages/content/src/moves`, `packages/test-tools/src/replay` and subpath exports in those three packages' `package.json`. Never create or edit those paths or those three `package.json` files, so the two branches merge cleanly.

## Constraints

- Keep the skeleton's rules: integer fixed-point simulation with no floating-point transcendental functions in the pure packages (an integer heading table written as literal data or generated by a script is fine), the server as the only writer, zod-validated protocol messages, and the private-match admission layers. Change the protocol version, since input changes.
- Use existing tooling: Colyseus `StateView` (or its 0.18 equivalent) for per-client visibility, Phaser for drawing, zod for data validation.
- The map is authored as a Tiled JSON map (`.tmj`, a documented subset) under `assets/source/maps/`. A script under `scripts/` converts it into a typed TypeScript module in `packages/content/src/`. The content package's tsconfig stays unchanged, so do not import JSON directly. A unit test fails when the generated module is out of date with the source map.
- Placeholder art only: coloured tiles and shapes drawn by Phaser, no image files.
- Out of scope: walking on islands, ruins, rubbings, loot, rumors, encounters, fruit, economy, match phases.

## Acceptance

- Map content, validated by unit tests that fail on a broken map:
  - four small islands, each with at least one dock; shoals as obstacles; eight spawn slots on the outer sea;
  - every dock and spawn slot reachable by sea;
  - at full speed on the shortest sea path, neighbouring islands 20–40 s apart and the longest useful crossing at most 90 s;
  - adjacent spawn slots out of engagement range (a named content constant).
- Sailing, unit-tested in `packages/simulation`: throttle forward accelerates to a maximum speed, braking decelerates, turning changes an integer heading at a turn rate, and a ship never enters a land or shoal tile. A collision stops or slides the ship without tunnelling, including at full speed. Docking works with interact near a dock at low speed: it stops the ship and records the dock; any throttle undocks. The whole state stays integer, and the determinism test still holds.
- Visibility, proven on real clients: an integration test with headless clients shows that a ship outside the sight radius is absent from the other client's decoded state, appears when it sails within the radius and disappears when it leaves. A player's own ship is always visible, and terrain needs no sync because the map is static content.
- Browser: the web client draws the tile map, follows the player's ship with the camera, lists and draws only visible ships, shows the docked state in the HUD, and has a minimap whose fog clears around the player's path (client-side is fine, as terrain is public). The four browser scenarios in `policy.json` pass: `join-private-match`, `two-ships-sync`, `sail-and-dock`, `out-of-sight`.
- Tests may place ships deterministically through a test-only server setting, for example an environment variable read only by the dev and test entry points. It is off by default and documented, and it never weakens admission or visibility.
- `docs/architecture.md` describes the map format and pipeline, sailing, docking and the visibility boundary, still within about a page and a half. `README.md` mentions the map script.
- `npm ci` then each of the five policy checks passes from a clean checkout.

# Decisions: world-sea

From the operator session of 2026-09-24 (slice planning after the skeleton merged into `main`). These are the recommended defaults; rerun `/workflow-grill world-sea` before launch to revise them.

## Decisions

- Scope is slice 2 of the plan: map, sailing, docking and server-enforced visibility, running in parallel with `duel-core`. On-foot island exploration, ruins, loot and encounters come later.
- One fullstack lane (`world`). A server/web split would fail the worker phase: typecheck gates each lane in isolation, and the web lane would compile against the server lane's new state types.
- The four slice islands follow §18 stage 2 ("four small islands"). The 12-island layout waits for the alpha.
- Map pipeline: Tiled JSON (`.tmj`) source in `assets/source/maps/`, converted by a script into a typed module in `packages/content/src/`, with a drift test. This follows §17 ("author maps in a tile editor and export a documented format") without changing tsconfig files the lane doesn't own.
- Sailing controls: up is throttle, down is brake (and slow reverse from a stop), left and right turn, E docks. These are §8's defaults for movement and interact.
- Visibility is enforced on the server per client (Colyseus `StateView`). Terrain is public static content, so the minimap fog is client-side. Enemy ships are the only hidden state in this slice.
- The existing browser scenarios keep their ids. `two-ships-sync` now means two ships within sight of each other, and the tests may use a test-only placement setting to get there.
- This feature owns the root `package.json`, the lockfile, `README.md` and `docs/architecture.md`; `duel-core` owns none of them, so the two branches don't conflict.

## Assumptions

- The sight radius is a content constant, about 10 tiles, and larger than the engagement range. The engagement range is also a content constant, used here only by the spawn validator.
- The integer heading resolution is the worker's choice (for example 64 or 256 directions) with a literal lookup table. Handling should feel generous rather than simulated (§3).
- `MatchRoom` keeps one room per match, the 1–8 player private matches and the three-layer admission from `skeleton-fixes`.
- The camera follows the player's ship. The map can be larger than the canvas.
- The patch rate stays at 20 Hz. `StateView` filtering must keep the room within its 60 Hz step budget with 8 ships.

## Deferred

- Walking on islands, ruins and rubbings, loot, rumors, fog secrets and the final island: `objectives-endgame`.
- Grapples and challenges (the engagement range as a mechanic): `encounters-theft`.
- The 12-island alpha map, landmarks, slow-zone hazards and sail tonics.
- Art: tilesets and ship sprites replacing the placeholder shapes.
