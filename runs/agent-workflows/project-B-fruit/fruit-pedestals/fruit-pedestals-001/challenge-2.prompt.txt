# Task: fruit

## Goal

Build the Devil-fruit acquisition rules of §9 as pure, deterministic code:
- the pedestals that hold fruit;
- the 3 s interruptible eating;
- the kit description a player can inspect before committing;
- the rule that a fruit, once eaten, stays for the match, with no swapping and no rerolls, and survives defeat.

Choosing a fruit is one of the match's biggest decisions, so it must be fair (first to finish eating wins a contested pedestal, deterministically) and it must never duplicate or lose a fruit. `fruit-kits-online` wires it into the room, carries the kit into duels and draws it. This feature only builds and proves the rules.

## Design (settled after design challenge attempt 1)

- **Shape: like the newer pure modules** (`stepClaim`, `stepEncounters`), not the old per-request ledger.
  - `createFruitState(sites, seed, preset)`, then each tick `stepFruits(config, state, { tick, players: [{ playerId, pedestalId | null, holding, reserved, disconnected, left }] }) → { state, results }`.
  - Inside the step: sort the players by the stable id comparison, advance every eating channel (a held tick at the same pedestal as the previous tick continues it; a gap, a different pedestal, a reservation or a disconnect resets it), then award completions in id order. A later completer at the same pedestal on the same tick gets `taken`.
  - Input order can never matter.
  - A stale or repeated tick is rejected with the very same state object.
  - `inspectPedestal` and `kitOf` are plain functions.
- **Which kits are dealt:** the fruit kits are `KIT_IDS` from `@pirate-sea-race/content/moves` minus `duelist` (today Ember and Smoke), with **two pedestals per fruit kit**. `createFruitState` refuses a preset whose `fruitKits` differs from that count, with a clear reason. So the slice (2) works, and the alpha (6) is refused until its four kits exist. Test that refusal.
- **Dealing:** the seeded generator deals the kits onto the caller's sites. The room must pass its **private** seed, never the public match code (§3, §16). Say so in the docs, and don't derive a seed internally. Each pedestal holds one fruit and is empty once eaten. Nothing respawns.
- **Descriptions:** `content/moves` has no kit descriptions, so `@pirate-sea-race/content/fruits` holds a short description per kit (Duelist, Ember, Smoke) from §9's table: the specials, the advantage, the vulnerability. `inspectPedestal` returns the kit id and its description. The caller decides who may inspect (players at that pedestal), and the docs say a pedestal's kit is only for players there.
- **Commitment:**
  - `kitOf(state, playerId)` is `duelist` for a player who hasn't eaten, **and for an unknown id** (documented).
  - After eating, it is that fruit's kit, and no second eat is possible.
  - This module has no defeat operation, so "defeat keeps it" means nothing here can clear it. A `left` player keeps their kit in the state, and their pedestal isn't refilled.
- **Eating time:** 60 held ticks (3 s), from content.

## Acceptance

Each item names the test that proves it. Tests live in `packages/simulation/src/fruits`.

1. **Dealing:** the same seed and sites give the same deal; two pedestals per fruit kit; the site count is validated (too few or too many is refused); the alpha preset is refused because its kit count doesn't match. Scripted and property tests.
2. **Eating:** scripted tests:
   - 60 held ticks eat;
   - a gap resets;
   - a reservation or disconnect resets;
   - already eaten, an empty pedestal and a disconnected player are refused;
   - moving to another pedestal resets;
   - stale or repeated ticks return the same state.
3. **Contested:** two players finishing on the same tick: exactly one fruit is given, to the lowest id, and the other gets `taken`, whatever order the players appear in the input (a symmetry test over permutations).
4. **Commitment:** `kitOf` is `duelist` before eating and the fruit after; nothing can change it after (no second eat); defeat and leaving keep it.
5. **Properties:** seeded random sequences of starts, holds, gaps, reservations, disconnects and leaves keep the invariants:
   - each pedestal is eaten at most once;
   - each player eats at most once;
   - the number of fruits eaten plus the full pedestals equals the pedestal count;
   - replay gives the same `hashState`;
   - an `EXERCISED` check covers every result.
6. **Content:** the constants (a 3 s eating time, 2 pedestals per kit) live in `@pirate-sea-race/content/fruits` with a zod validator. A content test refuses an eating time of 0.
7. **Docs:** `docs/fruits.md`, about half a page: pedestals, eating, contests, commitment, and how the room wires it (sites, per-tick facts, `kitOf` into duel creation).
8. `npm ci` then `npm run typecheck`, `npm run test:unit`, `npm run test:integration` and `npm run build` pass from a clean checkout, and the purity test covers the new directories.

# Decisions: fruit-pedestals

From the overnight session of 2026-09-25. The operator is asleep and asked the assistant to decide, record each decision, and use the workflow for the code.

## Decisions

- Fruit acquisition is built as pure rules first, in parallel with `rubbings-theft-fixes`. `fruit-kits-online` wires it (pedestal placement, the eating UI, the kit in duels, the arena drawing).
- Two pedestals per kit (§9's "two of each type"): the slice gets 2 Ember and 2 Smoke. The fruit is dealt by the match seed onto caller-supplied sites. Each pedestal feeds one player, once, and nothing respawns.
- Eating is a 3 s held channel, interrupted by a gap, a duel reservation or a disconnect. On contested completions, the lowest stable player id wins, deterministically.
- One fruit per player per match. It survives defeat and isn't returned on leaving. The default kit is the Duelist (§9: a deliberate choice, not a weak start).
- Eating doesn't end protection (§6 names objective collection, claiming and attacking; fruit is none of them).

- Corrected after design challenge attempt 1 (its alternative, adopted):
  - A per-tick `stepFruits` that sorts internally, so arrival order can't decide a contest.
  - The kits are `KIT_IDS` minus the Duelist, and a preset with a different fruit count (the alpha) is refused until its kits exist.
  - Descriptions live in `content/fruits`.
  - The deal takes the room's private seed.
  - An unknown player's kit is the Duelist.

## Assumptions

- The pedestal sites (probably island docks, like the rubbing sources) are chosen when it's wired, in `fruit-kits-online`.

## Deferred

- The room wiring, the eating UI, the kit description panel, the kit in sea duels, the arena drawing of Ember and Smoke: `fruit-kits-online`.
