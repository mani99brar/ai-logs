# Task: ledger

## Goal

Build the objective ledger of §4 as pure, deterministic code: the 12 rubbings with their stable ids, where each one is at every moment, and every operation that moves one (collection, duel settlement with theft, recovery caches). It must be impossible to lose or duplicate a rubbing, which §19's first launch gate requires. Later features wire it into the match room. This one only builds and proves the rules.

## Context

- Read `docs/spec.md` §4 (all of it), §11 (the PvP gold row, rounding, "Suppress gold rewards for repeated victories"), §12 (the defeat and disconnect table and "Details that prevent exploits"), §18 (the `slice` and `alpha` presets) and §19 ("Inventory correctness", "Disconnects").
- Read `docs/architecture.md` and `docs/duel.md`, the existing pure packages (`packages/simulation`: integer state, `hashState`, the seeded generator; `packages/content`: `rules.ts` with the `slice` and `alpha` rules presets and zod validators) and `tests/unit/purity.test.ts`.
- The verifier runs `npm ci`, then `npm run typecheck`, `npm run test:unit`, `npm run test:integration` and `npm run build`.
- Two other features run at the same time: `duel-online` (most of the repository) and `claim-channel` (`packages/simulation/src/claim`, `packages/content/src/claim`). Stay inside your owned paths.

## Constraints

- Owned paths only: `packages/simulation/src/objectives`, `packages/content/src/objectives`, `docs/objectives.md`, and `packages/simulation/package.json` and `packages/content/package.json` **only to add one subpath export each** (`@pirate-sea-race/simulation/objectives`, `@pirate-sea-race/content/objectives`, following the existing pattern with the `@pirate-sea-race/source` condition first). Do not change their `postbuild` scripts or dependencies, any existing source file, barrel, tsconfig or root file.
- Pure and integer like the rest of `packages/simulation`: no Phaser, Colyseus, DOM, timers, wall-clock time, `Math.random` or floating-point transcendental functions. Time is the world tick (20 per second) supplied by the caller; randomness only from a seeded generator kept in the state.
- Every operation is a function that takes the ledger state and a request and returns a new state plus a result; it never mutates its input. Requests that are duplicate, stale, unauthorised or already resolved return the current result without changing anything (§16).
- Out of scope: networking, rooms, rendering, ruins and their puzzles, rumors, shops, claims (`claim-channel`), the duel itself.

## Acceptance

- **State and invariant**: the ledger holds each rubbing's id, type and exactly one location: sealed at a source, owned by a player, held in a recovery cache, or reserved inside an unresolved duel (§4). Players hold at most one rubbing of each type. A function checks the invariant (every id present exactly once, one location each, no player holding a type twice), and every test calls it after every operation.
- **Content**: the four types (Sun, Moon, Tide, Storm) and the source assignment per rules preset: `slice` has 2 types and 8 rubbings, `alpha` has 4 types and 12 (3 of each). Assignment to islands is seeded and server-controlled, and it is zod-validated.
- **Collection** (§4): a player collects from an unlocked source by holding interact for 6 uninterrupted seconds. The ledger exposes start, progress and cancel as tick-driven operations; an interruption resets progress. A type the player already holds cannot be collected, and the rubbing stays sealed.
- **Duel settlement** (§4, §11): reserving a duel locks both players' rubbings. Settlement commits once, and validates eligibility again at commit time.
  - **Normal win:** the winner chooses one type the loser holds and the winner lacks, within a 5-second choice window. Without a choice, the default is the eligible type with the fewest free sources, then a fixed type order. The winner also takes 20 % of the loser's gold, capped at 50, rounded down and never negative. Gold is suppressed for a repeated win over the same opponent within 3 minutes, but theft still applies.
  - **No eligible type:** no rubbing moves, but the gold still transfers.
  - **Draw:** nothing moves.
  - **Repeated result message:** changes nothing.
- **Losses and caches** (§12):
  - Every loss grants the loser a fresh-rumor entitlement for the lost type (a flag the rumor system will read later).
  - When a disconnect reservation expires or a player quits, their remaining rubbings go into a recovery cache at a given position, without duplicating a rubbing that was just transferred.
  - A cache never despawns and disappears when empty.
  - Only a player missing a type can claim that rubbing from a cache, one rubbing per 6-second interaction.
  - Two players claiming the same rubbing at once can never both get it.
- **Property tests**: seeded random sequences of thousands of operations across all of the above (collections, interruptions, duels won, lost and drawn, choices and timeouts, repeated messages, disconnects, quits, cache claims) keep the invariant after every step. The final state hashes identically when the same seed is replayed.
- `docs/objectives.md` (about a page): the state shape, the operations, the invariant and the idempotency rules.
- `npm ci` then `npm run typecheck`, `npm run test:unit`, `npm run test:integration` and `npm run build` pass from a clean checkout, and the purity test covers the new directories.

# Decisions: objectives-ledger

From the operator session of 2026-09-24. The operator asked for parallel work beside `duel-online`, each run in its own tab. These are the assistant's recommended defaults; no separate grill was held.

## Decisions

- Scope is the pure rubbing ledger: §4 inventory, collection timing, duel settlement (theft choice and default, §11's PvP gold transfer with its repeat-win suppression) and §12 recovery caches. It is proven by property tests against §19's "Inventory correctness" and "Disconnects" gates, before any network exists.
- A separate feature from `claim-channel`, so the two run in parallel. The claim rules take "holds all four types" as an input rather than reading the ledger.
- The code lives in new directories behind subpath exports (`@pirate-sea-race/simulation/objectives`, `@pirate-sea-race/content/objectives`). The only shared file is each package's `exports` block, which the assistant reconciles at merge. At merge, the new subpaths are also added to `scripts/smoke-build.ts` (owned by `duel-online` now) to prove they load from `dist/`.
- One lane (`ledger`), checks typecheck, unit, integration and build, with no browser check.

## Assumptions

- Positions (sources, caches, docks) are integer sub-unit coordinates supplied by the caller; the ledger doesn't know the map.
- The fresh-rumor entitlement after a loss is recorded as data for the future rumor system.
- The `slice` preset (2 types, 8 rubbings) and the `alpha` preset (4 types, 12 rubbings) both work; the default is the one the match's rules preset names.

## Deferred

- Wiring into `MatchRoom`, ruins and their interactions, rumors and sightings, shops and the rest of §11's economy: `objectives-endgame`.
- Duel reservation mechanics from the sea: `encounters-theft`.
