# Task: flow

## Goal

Build the match's lifecycle as pure, deterministic rules: the §2 phases from lobby to results, the match timer, how a match ends (a claim, the deadline, everyone leaving, a server fault), and the **results** a player sees at the end: the winner or "no winner", plus each player's exploration and duel accomplishments. These rules decide how a match begins and ends. The wiring feature (`objectives-endgame`) drives them from the room and shows the lobby countdown, the timer and the results screen. This one only builds and proves the rules.

## Design (settled)

- **Phases:** `lobby` → `ready` → `departure` → `exploration` → `ended`.
  - **`lobby`:** players join and leave. A **public** match needs its full preset (8 seats) to move on; a **private** match can start with 2 to 8 players when the host asks, and is marked `custom` (§2). Late joiners after `lobby` are refused (§2: they wait for another match).
  - **`ready`:** a 20 s countdown during which clients preload (§2). If a player leaves during `ready`, a private match continues if it still has 2 or more players, and a public one returns to `lobby`.
  - **`departure`:** starts at **control start**. The module emits `control-started` with the tick, which the caller passes to the claim config and to the encounter rules for the 45 s spawn protection. `departure` lasts 45 s, then becomes `exploration`, with no gameplay change; it's a label for the HUD.
  - **`exploration`:** runs until the match ends.
  - **`ended`:** has a reason: `claim` (the caller reports the claim module's winner), `deadline` (the claim module's `match-ended` with no winner), `abandoned` (every player has left, §12: no winner), or `aborted` (the caller reports a server fault, §12: no winner, no competitive penalty). The first end wins, later reports change nothing, and a claim on the deadline tick beats the deadline (§2, as the claim module orders it).
- **Timer:** `elapsed(state, tick)` and `remaining(state, tick)` count from control start, for a HUD that shows 35:00 counting down. The match timer never pauses (§2).
- **Results**, built when the match ends:
  - the reason and the winner (or none);
  - per player: rubbings collected, thefts made, rubbings lost, duels won, lost and drawn, gold at the end, caches claimed, and islands visited.
  - The caller feeds these as events during the match (a small typed event union: `collected`, `stole`, `lost`, `duel-ended`, `cache-claimed`, `island-visited`, `gold`), and the module counts them.
  - Results are deterministic, sorted by a stable order: the winner first, then by rubbings held at the end, then by player id.
  - A player who left still appears, marked `left`.

# Decisions: match-flow

From the overnight session of 2026-09-25. The operator is asleep and asked the assistant to decide, record each decision, and use the workflow for the code.

## Decisions

- The match lifecycle is built as pure rules, like the other modules, in parallel with `rubbings-theft`. The endgame wiring drives it.
- Phases: lobby → ready (20 s preload) → departure (45 s, spawn protection, granted by the encounter rules) → exploration → ended.
- Private matches start with 2–8 players on the host's request and are marked custom. Public matches need all 8 seats (§2).
- There are four endings: claim, deadline (no winner), abandoned (everyone left: no winner), and aborted (a server fault: no winner, no penalty). The first end wins.
- The results show the winner or "no winner" plus per-player accomplishments, so a timeout still feels like a finished match (§2).
- The module doesn't duplicate the claim deadline or spawn protection. It emits `control-started`, and the other modules own their rules.

## Assumptions

- The per-player stats are fed as events by the caller, and the module only counts them.

## Deferred

- The lobby UI, the timer HUD, the results screen and the room wiring: `objectives-endgame`.
- Public matchmaking and the queue (§2's public lobby): after stage 2.
