Any CLI reporting boundary other than `export` degrades a run recorded before configured lanes. `workflow status <run>` (and every other action in pipeline.main that ends in report()) builds the new graph over a plan without `workers`, calls get_state, and LangGraph drops the checkpoint's `ui`, `adapter`, `ui_packet` and `adapter_packet` channels because PipelineState no longer declares them. report() then calls export_state() directly, which writes run-state.json at version 1.3.0 with `values` lacking both `lanes` and `packets`; the raw-checkpoint carry that rescues this evidence lives only in export_run() (workflow/pipeline.py:545-555) and is not reached from report() (workflow/pipeline.py:627-629, 846). For a finished legacy run such as project-workflows-001 the previous export had the flat keys, so the comparison in export_state sees a change and overwrites the file. The viewer then projects launch_ui/launch_adapter and verify_ui/verify_adapter as `paused` (server/projects.ts hasEvidence false with a succeeded event) and loses the launch session ids, contradicting the legacy-run scenario that the viewer renders the old run identically. Recoverable only by running `workflow export` afterwards. report() should apply the same legacy carry as export_run(), or status should route through export_run().
