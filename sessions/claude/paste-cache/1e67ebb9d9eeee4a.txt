Design challenge attempt 1 paused the run before any worker launch. Concerns:
  P1 [failure_mode] The plan checks the code in the room itself (instance onAuth/onJoin). Colyseus runs those only after its HTTP matchmaker has already reserved a seat and sent the reservation back to the caller. A `join` or `joinOrCreate` without a code gets no `filterBy` filter, and a `joinById` to any known roomId is also allowed. All of these still receive a reservation for some private match. In Colyseus, that reservation carries the room's listing, and the listing (RoomCache.toJSON) includes `metadata`. `MatchRoom.onCreate` puts `{ code }` into that metadata (apps/server/src/MatchRoom.ts:86). So a caller without the code can read the code from the reservation's JSON, get refused when the WebSocket connects, then join again with the code. Each unused reservation also counts toward `maxClients` until `seatReservationTime` runs out. So repeated HTTP-only joins can fill any private match, and real players with the code get the 409 'full' refusal. Today's static onAuth (MatchRoom.ts:47-49) lets every code-less request through as a 'create'. Neither the task nor decisions.md says code-less, token-less requests must be refused before a seat is reserved.
      Consequence: All of finding 1's acceptance tests pass: code-less and wrong-code joins are refused with a readable message, the creator gets in, the room keeps running. Yet a private match is still joinable without knowing its code, and can be filled up by anyone. The independent review would block the candidate again on the same P1.
  P2 [assumption] Finding 9 is already fixed in this base. `mapBounds` returns `widthTiles * subUnitsPerTile - 1` (packages/simulation/src/config.ts:15). `simulation.test.ts:129-140` already checks that a ship clamped to the far corner lies on tile `widthTiles - 1` and `heightTiles - 1`. The task describes the older, inclusive version.
      Consequence: A worker trying to 'fix' finding 9 could subtract another 1, which would break the existing test or leave a dead row of sub-units. Or it could spend time looking for a bug that isn't there. The worker should confirm the fix, point to the existing test, and change nothing.
  P2 [failure_mode] The unknown-code refusal must stay in the static onAuth: the `matchMaker.query` lookup that throws a 404. It must not be moved entirely into the room. The e2e test expects exactly 'No match with that code' for an unknown code (tests/e2e/private-match.spec.ts:71). If the static check goes, that request fails with MATCHMAKE_INVALID_CRITERIA, which finding 3 changes to show 'That match is full or no longer exists'.
      Consequence: The browser check fails on the join-error text, or the worker edits the e2e expectation, which the constraints forbid.
  P2 [failure_mode] The build smoke script starts a long-lived child process. It has to kill that child on every failure path: health check timeout, SDK error, assertion failure, or an exception. Every wait needs a time limit. For the port, run the server with PORT=0 and read the real port from main.ts's 'listening on ws://localhost:N' line; that avoids the race in picking a free port first and binding it later.
      Consequence: A smoke failure could leave an orphaned server running, or hang `npm run build` until the verifier's 600 s timeout. The verifier would then report a timeout instead of the actual error, and in the worst case the orphan could interfere with the browser check that runs next.
  P2 [assumption] When the room refuses a seat by throwing in onJoin or instance onAuth, the refusal happens after the WebSocket is open. Depending on the Colyseus 0.18 path, the message may reach the client as a WebSocket close reason, which the protocol caps at 123 bytes. Room-level refusal messages should stay short, and the integration tests should assert on the exact text.
      Consequence: A long message could be cut off, or `ws` could throw while closing. The client would then show a generic or empty error, and the 'readable message' acceptance for finding 1 would fail or be flaky.
Simpler alternative: Close the hole in the matchmaker before a seat is reserved, and keep the room-level check only as a backstop:
(a) In the existing static `onAuth`, refuse with 400 any request that has neither a well-formed `code` nor a `createToken`. Refuse a request that has both.
(b) Register `filterBy(["code", "createToken"])`, and never put the token into metadata. A request carrying a token then matches no existing listing: `join` fails and `joinOrCreate` can only create, so it never gets a seat in someone else's match.
(c) Keep the instance `onJoin` check: the token must equal the one stored in `onCreate` (the creator's seat only), or the code must equal `this.state.code`. This catches `joinById`.
The only leak left is `joinById` by someone who already knows a roomId, which today means a current or former member. Record that in docs/architecture.md. This is about the same amount of code as the plan, and it stops both the code leak and seat-squatting. Room-level checks alone stop neither.
