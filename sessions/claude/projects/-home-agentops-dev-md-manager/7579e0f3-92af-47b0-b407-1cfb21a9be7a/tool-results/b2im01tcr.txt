    attach-one follows a session an update respawned under a new PID
    
    A Claude Code update restarts the background service, which adopts the
    running sessions and about 15 seconds later respawns the idle ones onto the
    new binary under new PIDs (daemon.log: "adopted=2", then "post-takeover
    prewarm burst - respawned 1/2 stale workers"; the ui lane of
    workflow-guardrails-001 was frozen under a PID it was not launched with).
    attach-one only waited while the PID it had attached was still alive, so a
    respawn left the pane dead: exit 1 then a row without a PID raised "No live
    native PID"; exit 1 then a failing listing re-raised it; exit 0 ("Session
    <id> has exited.") then the new PID returned silently; exit 1 then the row
    still listing the dead PID refused the session.
    
    The wait now depends on the background id, not on its old PID: once the id
    was verified live and attached and no stop is recorded, attach-one waits out
    a failing listing (any error, classified by where it comes from), a row
    still registering its PID or in a non-terminal state other than the
    attachable ones, and, for 30 seconds from when it first saw it, a row still
    listing an ended PID. A live row under a different PID is a respawn, so it
    is reattached even after exit 0: an operator's detach never changes the PID
    (an interrupted attach, 130 or SIGINT, still ends attach-one). It still
    refuses at once a first attach, a successful listing without the id once the
    attached process ended, a stopped or failed row and every identity refusal,
    and it still attaches nothing without a verified live row. An attach that
    held for a minute starts a new count however it ended, so a respawn after
    hours attached does not count towards the limit.
    
    From the same review: the stop records are read again right after the
    listing, immediately before each `claude attach`, which narrows the race
    with the controller's freeze; an unconfirmed stop intent now says the
    controller is stopping the node and how to inspect it (`claude logs <id>`,
    `claude attach <id>`); and the give-up message ends with the last error
    (the listing's, the refusal's or the attach's). The RUNBOOK says so.
