Stops and outages: record only confirmed stops, stop every lane, exit 75 only when resumable

A final review of round 3 confirmed three P2 defects in how the controller
stops sessions and classifies Claude Code outages.

A `claude stop` that ran and exited non-zero kept `issued: true`. That is
what a restarting background service does before it respawns the session
under a new PID. A retry in that respawn gap found the session missing from
the listing and its old PID ended, then saved `stopped: true` without
issuing any stop, so the respawned session kept running. stop_session now
clears `issued` when the stop fails. The retry then looks through the gap
(UpdateGaps) and stops the respawned process once, and it records nothing
while the gap lasts.

stop_workers raised at the first lane whose stop failed. After a blocked
wait, that is usually the lane that blocked it (a `stopped` or `failed`
row, a changed identity), so every later lane kept running and using quota.
It now attempts every lane, then raises all the failures together, each
named by lane. The combined error is a TransientInfraError only when every
failure was one, so an interrupted freeze stays resumable. Any other
refusal decides the run.

Every TransientInfraError out of the graph exited 69/75 with "Nothing was
stopped ... resume", even when the node had already ended on it for good:
a print review terminates its jobs and blocks, and a reviewer launch or
rebind is left at needs_reconciliation. The resume then stopped at
"Non-retryable graph failure". drive now raises (exit 69, then 75) only for
a state the next controller continues: an interrupted freeze, an
interrupted native review, or an accepted review whose stops are still
owed. Otherwise it records a `controller blocked` event naming the outage
and classifies the failure like any other, so `automatic` exits 1.
rebind_reviewers now treats an outage while a resume rebinds a reviewer as
an interruption: it keeps the reviewer running and sets the review's
interrupted marker, instead of marking it needs_reconciliation. A second
outage during a resume therefore stays resumable, as RUNBOOK describes.

RUNBOOK and the TransientInfraError docstring now describe this behaviour.
