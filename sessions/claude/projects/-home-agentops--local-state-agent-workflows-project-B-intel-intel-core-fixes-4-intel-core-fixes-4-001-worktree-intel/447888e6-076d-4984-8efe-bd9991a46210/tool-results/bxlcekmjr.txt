=== intel-core
# Task: intel

## Goal

Build the match's information systems as pure, deterministic rules. They tell a player where to go and when the race tightens:
- rumors that point toward a missing rubbing type;
- the journal that marks stale leads and offers replacements;
- coarse, delayed carrier sightings;
- the sea sectors;
- the timed reveals of §2 (the final-island sector when a first full set exists, minute-20 reveals, minute-28 carrier sectors every 30 s).

This information is what turns exploring into a race and brings players into conflict, so it must be useful but never a free tracker. Every output is addressed to specific players (§16). `objectives-endgame` wires it into the match room later. This feature only builds and proves the rules.

## Constraints

- Owned paths only: `packages/simulation/src/intel`, `packages/content/src/intel`, `docs/intel.md`, and `packages/simulation/package.json` and `packages/content/package.json` **only to add one subpath export each** (`@pirate-sea-race/simulation/intel`, `@pirate-sea-race/content/intel`, following the existing pattern with the `@pirate-sea-race/source` condition first). Do not change their `postbuild` scripts, dependencies, any existing source file, barrel, tsconfig or root file.
- Independent of the ledger's code: the caller passes a per-tick **world view** (for each rubbing, its type and where it is: a sealed source with its island, a cache position, a carrier with position, or reserved in a duel; each player's held types and position; which islands are claimed out). Don't import `objectives`, so the two stay decoupled. Gold for bought rumors is the caller's (ledger) business; this module only generates the rumor.
- Pure and integer: no Phaser, Colyseus, DOM, timers, wall-clock time, `Math.random` or floating-point transcendental functions. Time is the world tick (20 per second). Randomness comes from the seeded generator (`random.ts`). Durations are named content constants in seconds, converted to ticks.
- The step shape: `stepIntel(config, state, worldView, requests) → { state, messages, outcomes }`. Every message names its recipients: one player, several, or everyone. It never mutates its input.
- **Targeted rumor requests** are `{ requestId, playerId, type }`. Each gets exactly one outcome, `{ requestId, result: "rumor" | "sighting" | "capped" | "none" | "duplicate" }`, so the caller charges 25 gold only for `rumor` or `sighting`. A repeated `requestId` is answered `duplicate` without changing the state or using the generator. An exported pure `targetedRumorAvailability(config, state, worldView, playerId, type)` lets the UI show whether buying would yield anything.

## Design (settled)

- **Sectors.** The map is divided into a 3 × 3 grid of named sectors (for example "North-West Reach", "Central Waters"), computed from the map size in the config. `sectorOf(position)` is total and deterministic on the boundaries.
- **Rumors.** A rumor names a missing type and a target: an **island** (a sealed source of that type there) or a **sector** (a cache or a carrier). It never names a rubbing id or an exact position. Generation picks, deterministically from the seed, among the eligible targets for a type the player lacks. It prefers sealed sources, then caches, then a carrier sighting. It never picks a target that is the player's own inventory. Rumors are made in four cases:
  - a **starting rumor** for each player at control start (§2);
  - a **fresh rumor** when the world view shows a type was stolen from the player (§11);
  - a **targeted rumor** on request, gold-gated by the caller (§11);
  - a **replacement lead** from the journal.
- **Two kinds of lead.**
  - **Journal rumors** target only islands (sealed sources) or cache sectors. Only these go stale: when the target no longer holds a copy of that type, the rumor is marked stale (a message to its holder, with the tick), and the journal offers a replacement from the remaining sources and caches.
  - A **carrier sighting** is a one-shot message: the sector where a carrier of that type was 30 s earlier, never the current one. It is **never** tracked for staleness, so carrier movement can't leak live information. It is sent only on three triggers: a fresh rumor after a loss when every other copy is carried, a targeted rumor under the same condition, or a journal replacement when every remaining copy is carried. At most one carrier sighting per player per carrier interval (30 s) before minute 28.
  - A rumor whose type its holder has since obtained is retired quietly (a "resolved" message, no replacement).
- **Carrier snapshots (not a rolling history).** At each 30 s carrier boundary counted from control start (crossing-based), the state takes one snapshot: the sector, type and internal holder of each carried copy. It keeps only the latest two. A carrier sighting reads the **older** snapshot, so it is 30–60 s old and never the current location, by construction. The minute-28 broadcast reads the newer one. Snapshot entries held by the requester themselves are never used for that requester's sighting.
- **The sighting cap** lines up with the snapshots: at most one sighting per player per snapshot, before minute 28. A **free** trigger (a fresh rumor after a loss, or a journal replacement) that hits the cap is **deferred**, not dropped: it is delivered at the next snapshot boundary (at most one pending per player).
- **Held types include rubbings reserved in a duel**, as the ledger's `heldTypes` counts them. So entering a duel is never a "loss", and only a settled theft is.
- **What sightings and broadcasts contain:** a sector and a rubbing type, never a player id, a rubbing id or an exact position.
- **Losses and completions come from diffing** each player's held types between ticks. The ledger's sticky `freshRumors` flag isn't used as a signal.
- **Robust to skipped ticks:** reveals and intervals fire when a boundary is crossed since the last processed tick (`>=`), not on equality, so a skipped or batched tick never loses one.
- **Timed reveals** (§2), counted from control start (`controlStartTick` in the config):
  - **The first full set:** when a player first holds all the preset's types, everyone gets the final island's sector, and that player gets the exact final-island position (their "route"). If they lose a type, their route becomes inactive until the set is restored. A later completer gets their own route message. The final island's position comes from the config.
  - **Minute 20:** everyone gets the sectors that contain unclaimed rubbings (sealed sources) and abandoned caches.
  - **Minute 28 on:** every 30 s, everyone gets the approximate sectors of rubbing carriers.
  - **Minute 35:** nothing here; the claim code ends the match.
- **Hidden information.** No message to a player contains another player's exact position, a rubbing id or a source's exact location. The only exact position ever sent is the final island's, and only to a complete-set player. A test asserts this over every message of every property run.

## Acceptance

Each item names the test that proves it. Tests live in `packages/simulation/src/intel` unless noted.

1. **Sectors:** every map cell maps to exactly one of nine sectors; the boundaries are deterministic; the names are unique.
2. **Rumors:** scripted tests for each of the four cases:
   - targets prefer sources, then caches, then carriers;
   - there is never a rumor for a type the player holds, and never one pointing at the player's own inventory;
   - the same seed gives the same rumor.
3. **Staleness and the journal:** scripted tests:
   - an island or cache target emptied by collection (a source collected, a cache claimed) goes stale, and the journal offers a replacement from the remaining sources and caches;
   - a rumor whose type the holder then obtains (by collection or theft) is resolved, not stale;
   - with every copy carried, the replacement is a carrier sighting from the older snapshot (30–60 s old, never current);
   - a capped free trigger is delivered at the next boundary;
   - the targeted-request outcomes cover all five results, including `duplicate` with the very same state.
4. **Reveals:** scripted tests at the exact boundary ticks:
   - the first full set, including a lost-then-restored set and a second completer;
   - minute 20;
   - minute 28, then every 30 s;
   - nothing before control start.
5. **Hidden information:** seeded property runs (random worlds with players collecting, stealing, caching and moving) check every message against the rules in the design:
   - at least one seed runs the real constants for 36,000+ ticks, past minute 28 plus several carrier intervals; the other seeds use a config with compressed reveal times;
   - no message has an id or an exact position (except the final island to a full-set holder);
   - no player gets more than one carrier sighting per snapshot before minute 28;
   - no stale message is ever sent for a carrier sighting;
   - some runs skip ticks. The state replays to the same `hashState`. An `EXERCISED` coverage check asserts that every message kind occurred.
6. **Content:** the constants (the sector grid 3 × 3, the sighting delay 30 s, the reveal times 20 min and 28 min, the carrier interval 30 s, the sector names) live in `@pirate-sea-race/content/intel` with a zod validator. A content test refuses a carrier interval of 0 and reveal times out of order.
7. **Docs:** `docs/intel.md`, about a page: sectors, rumor generation and staleness, the reveal schedule, the message addressing, and how the caller builds the world view from the ledger.
8. `npm ci` then `npm run typecheck`, `npm run test:unit`, `npm run test:integration` and `npm run build` pass from a clean checkout, and the purity test covers the new directories.

## Decisions

- The information systems are built as pure rules first, in parallel with the online work. `objectives-endgame` wires them in.
- There are nine named sectors (3 × 3), computed from the map size, so the same code serves the slice sea and the 12-island alpha.
- Rumors never name ids or exact positions. They prefer sealed sources, then caches, then a carrier sighting. Carrier sightings come from a snapshot 30–60 s old (never current), which helps a player choose a route without giving them a tracker (§11).
- The module reads a caller-built world view instead of importing the ledger, the same decoupling as the claim code.
- The only exact position ever sent is the final island's, and only to a player holding a full set (§5).

- Corrected after design challenge attempt 1 (its alternative, adopted): carrier sightings are one-shot and never go stale, at most one per player per 30 s before minute 28, so a victim can't track the thief. Only island and cache rumors go stale. Broadcasts carry a sector and a type, never a player. Losses come from diffing held types. Reveals fire on crossing boundaries.

- Corrected after design challenge attempt 2: stale means emptied by collection (theft can't empty an island or a cache); targeted rumors carry a request id and get an outcome, so gold is charged only when something is delivered and retries can't double-spend (§11); carrier data comes from two 30 s snapshots, so a sighting is 30–60 s old, a deliberate small relaxation of "exactly 30 s"; capped free sightings are deferred, never dropped; duel-reserved rubbings still count as held.

## Assumptions

- The final island's position and the control start tick come from the config (the final-island sockets arrive with `objectives-endgame`).
- The slice uses two rubbing types, so "all types" means both, per the preset.
