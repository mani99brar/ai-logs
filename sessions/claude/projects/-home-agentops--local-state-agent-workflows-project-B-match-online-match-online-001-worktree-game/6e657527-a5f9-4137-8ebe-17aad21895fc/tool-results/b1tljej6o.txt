# Match flow

§2's match lifecycle as pure, integer rules: the phases from lobby to results, the match timer, the four ways a match ends, and the per-player results. The rules live in `packages/simulation/src/match` (`@pirate-sea-race/simulation/match`) and their tuning in `packages/content/src/match` (`@pirate-sea-race/content/match`). Nothing is wired into the match room yet: `objectives-endgame` will drive them and show the lobby countdown, the timer and the results screen.

## Content

`matchRules` holds the tuning in world ticks (20 a second) and seats, and `validateMatchRules` checks it with zod:

| Rule | Value | Source |
| --- | --- | --- |
| `readyTicks` | 400 (the 20 s ready check, while clients preload); must be positive | `READY_COUNTDOWN_SECONDS` |
| `departureTicks` | 900 (45 s): the encounter rules' `SPAWN_PROTECTION_SECONDS`, not a copy | `DEPARTURE_SECONDS` |
| `publicSeats` | 8, the alpha preset's `maxPlayers`: public matches never start short-handed | `PUBLIC_SEATS` |
| `privateMinPlayers` / `privateMaxPlayers` | 2 / 8 (§2: private tests start with two to eight) | `PRIVATE_MIN_PLAYERS`, `privateMatch.maxPlayers` |

`createMatchConfig({ kind, rules?, durationTicks?, startingGold? })` builds a match's `MatchConfig`. `kind` is `public` or `private`, and a private match is `custom`. `durationTicks` defaults to the claim rules' `deadlineTicks` (42 000) and only feeds the timer: the deadline itself comes from the claim module. `startingGold` defaults to the objective rules' 50.

## Phases

`lobby` → `ready` → `departure` → `exploration` → `ended`. Only `ready` can go back, to `lobby`.

- **`lobby`.** Players join and leave. A join beyond the seats is refused (`full`). A public match enters `ready` on the tick its eighth seat fills, and a start request in it is refused (`public`). In a private match the first joiner is the host (when the host leaves, the earliest joiner still present takes over, `host-changed`). The host's `start` enters `ready` with 2 or more players present. Otherwise it is refused (`too-few`, or `not-host` from anyone else).
- **`ready`.** Lasts `readyTicks`. A join is refused (`started`), and so is any join after the lobby (§2: late arrivals wait for another match). When players leave, a private match keeps counting down with 2 or more present, a public one needs all 8, and otherwise it returns to `lobby`. A later start begins a new countdown.
- **`departure`.** Starts at control start, `readyTick + readyTicks`. The step emits `control-started` with that tick, exactly once. `departure` lasts `departureTicks`, then becomes `exploration`. This is only a HUD label and changes no gameplay.
- **`exploration`.** Runs until the match ends. The module never ends it by time alone.
- **`ended`.** Has an `end` (`reason`, `winner`, `tick`) and the `results`.

A player who leaves before control start is removed. After it, they stay in the state, marked `left`, and appear in the results. `leave` means the seat is released (§12: an explicit quit or an expired 60 s reservation), not a disconnection.

## A step

`stepMatch(config, state, input)` returns `{state, events}` and never changes its arguments. `input` is `{tick, reports}`:

- `tick` must be after the state's tick. Later ticks may skip ahead. A tick at or before the state's, whether stale or repeated, returns the same state object and no events, as does any input once the match has ended. So the first end wins, and nothing arriving later changes it.
- A step runs in a fixed order:
  1. The timed transitions due by `tick`, each on its own scheduled tick (a skipped-over control start is still reported at `readyTick + readyTicks`).
  2. The reports, in list order.
  3. The end, if any.
  4. With no end, the lobby and ready rules. Start requests are judged after all joins and leaves of the tick.
- Malformed reports throw a `RangeError`: an empty id, negative or fractional gold, a duel against oneself or won by an outsider, an accomplishment by an unknown player, a claim for an unknown winner, a claim end whose `tick` is not the input's, or an unknown kind.

### Reports

| Report | Fields | Effect |
| --- | --- | --- |
| `join` / `leave` | `playerId` | As in the phases above. A repeat join, or a leave by someone absent, is ignored |
| `start` | `playerId` | The private host asks to start |
| `collected`, `stole`, `lost`, `cache-claimed` | `playerId` | Count one rubbing collected from a source, taken from a duel loser, lost (to a thief or into a recovery cache), or claimed from a cache |
| `island-visited` | `playerId`, `island` | Adds a distinct island id |
| `gold` | `playerId`, `gold` | Sets the balance |
| `duel-ended` | `playerIds: [a, b]`, `winner` or `null` | A win and a loss, or a draw for both |
| `match-ended` | the claim module's event, unchanged: `tick`, `reason` (`claim` or `deadline`), `winner` | Ends the match. Ignored before control start |
| `fault` | none | §12's server fault: `aborted` |

Accomplishments count only from control start until the end.

### Endings

| Reason | When | Winner |
| --- | --- | --- |
| `claim` | The claim module's `match-ended` with a winner | That player |
| `deadline` | The claim module's `match-ended` at its deadline (§2) | None |
| `aborted` | A `fault`, in any phase (§12: no competitive penalty) | None |
| `abandoned` | No player is present after the lobby (§12). An empty lobby just stays open | None |

On one tick the precedence is claim, then deadline, then aborted, then abandoned. A claim completing on the deadline tick therefore beats the deadline, as the claim module orders it.

### Events

`player-joined`, `join-refused` (`started` or `full`), `player-left`, `host-changed` (`playerId` or `null`), `start-refused` (`public`, `not-host`, `too-few`), `phase-changed` (`from`, `to`), `control-started`, and `match-ended` (`reason`, `winner`, `results`). The results are emitted once and are the same object as `state.results`. Every event carries `tick`.

## Wiring with the claim and encounter rules

The room steps the match every world tick with that tick's reports. On `control-started` it:

1. builds the claim config with `createClaimConfig({ claimPoint, controlStartTick: tick })`, whose `deadlineTick` is `tick + 42 000`;
2. grants every ship the encounter rules' spawn protection (45 s) from the same tick;
3. starts the intel and objective clocks from it.

It then steps the claim rules on each tick and passes their `match-ended` event into the same tick's match input. It never duplicates the deadline, the protection or the claim ordering. It also forwards ledger outcomes (collections, thefts and losses, cache claims, gold) and duel settlements as reports, and `fault` when the process detects one.

## Timer

`elapsed(state, tick)` and `remaining(state, tick)` are world ticks counted from control start, so the HUD shows 35:00 counting down. Before control start, `elapsed` is 0 and `remaining` the full duration. The timer never pauses (§2). It is frozen at the end tick once the match has ended, and neither value goes below 0.

## Results

`MatchResults`: `reason`, `winner` (or `null`: "no winner"), `tick`, `custom`, `elapsedTicks` (from control start to the end, 0 if control never started), and `players`. Each player line has `id`, `winner`, `left`, `rubbingsHeld` (collected + thefts + cachesClaimed − lost, at least 0), `collected`, `thefts`, `lost`, `duelsWon`, `duelsLost`, `duelsDrawn`, `gold`, `cachesClaimed` and `islandsVisited`. Lines are ordered with the winner first, then by rubbings held (most first), then by id in UTF-16 order. The state is plain integer data that `hashState` covers. `replayMatch(config, state, inputs)` steps a list of inputs and returns the final state, every event and the hash.

## Tests

- `packages/simulation/src/match/match.test.ts`: scripted tests with frozen inputs covering every transition, the public and private start rules, late joiners, leaving during `ready`, `control-started` (also when skipped over), each ending and its precedence, the timer, and the exact results of a match that feeds every report kind.
- `property.test.ts`: 60 seeded matches (public and private, with skipped ticks, repeated inputs, joins, leaves, starts, accomplishments, claims, faults and deadlines). It checks that the phase only moves forward (except `ready` → `lobby`), that there is at most one end, and that the results are built exactly once and match an independent tally. It also checks replay hashes, including replays with repeated inputs, and an `EXERCISED` check over every phase, end reason and refusal.
- `packages/content/src/match/match.test.ts`: the constants and the validator, including a refused ready countdown of 0.
# Claim

The §5 treasure claim as pure, integer rules: who may claim, the ten-second channel, what resets it, and how same-tick events and §2's deadline are ordered. The rules live in `packages/simulation/src/claim` (`@pirate-sea-race/simulation/claim`) and their tuning in `packages/content/src/claim` (`@pirate-sea-race/content/claim`). Nothing is wired into the match room yet.

## Content

`claimRules` holds the tuning in world ticks (20 a second) and tiles, and `validateClaimRules` checks it with zod:

| Rule | Value | Source |
| --- | --- | --- |
| `channelTicks` | 200 (10 s); 0 means instant victory on arrival, §5's alternative | `CLAIM_CHANNEL_SECONDS` |
| `deadlineTicks` | 42 000 (35 min after player control starts) | `MATCH_DURATION_MINUTES` |
| `circleRadiusTiles` | 4, a placeholder until playtests (below the 6-tile engagement range) | `TREASURE_CIRCLE_RADIUS_TILES` |

`createClaimConfig({ claimPoint, controlStartTick?, subUnitsPerTile?, rules? })` turns them into a match's `ClaimConfig`: the claim point and circle radius in sub-units, the channel length and the absolute deadline tick. The caller picks the final island's claim point. `subUnitsPerTile` defaults to the sea map's and must be a positive integer.

## State

`ClaimState` is plain integer data that `hashState` covers entirely:

- `tick`: the last world tick processed. `createClaimState(config, tick = 0)` starts before the deadline.
- `channel`: the one active channel or `null`: `playerId`, `startTick`, the position `x, y` the channeller stopped at, and `progress`, the ticks held since `startTick`.
- `result`: `null` while the match runs. Then `{reason: "claim", winner, tick}` or `{reason: "deadline", winner: null, tick}`, set once.

## A tick

`stepClaim(config, state, input)` returns `{state, events}` and never changes its arguments. The caller supplies each tick's `input`:

- `tick`: the state's tick plus one (anything else is refused).
- `players`: `{id, x, y, speed, holdsAllTypes, interact, connected, protected}` for each relevant player. `holdsAllTypes` comes from the ledger, so this module does not depend on it. A player missing from the list counts as disconnected.
- `encounters`: every accepted encounter reservation on this tick, newly accepted or still running, as `{id, playerIds: [a, b]}`. A player may be in only one of them.

Both lists are read as sets. Ids compare by UTF-16 code unit (so `"B" < "a"` and `"p10" < "p9"`), never by locale. Malformed input (duplicate ids, non-integers, a player in two encounters) throws a `RangeError`.

Once `result` is set, the step returns the same state object and no events, whatever the input, so nothing arriving after a win can cancel it. Otherwise it runs five phases in order:

1. **Reservations.** If the channeller is in an encounter, the channel resets (`duel`). This comes before the channel phase, so a duel accepted on the tick a claim would complete stops the claim.
2. **The active channel.** It breaks if the channeller is absent or disconnected (`disconnected`), no longer holds all four types (`ineligible`), has a nonzero speed or has moved from where the channel started (`moved`), or has released interact (`released`), checked in that order. Otherwise `progress` goes up by one. A break always resets progress to zero because the channel is discarded.
3. **Starting.** With no channel active, including one that broke earlier in this tick, a player may start if they are connected, hold all four types, hold interact, are not reserved, have speed 0 and are inside the treasure circle (squared distance ≤ radius², so the edge counts). If several can start, the closest to the claim point wins, then the lowest id. Other eligible players wait, and they start on the first tick the channel is free. A protected player may start: the step emits `protection-ended` before `claim-started`, and protection is not read again during the channel (§6: claiming ends protection first). A player who is waiting keeps their protection.
4. **Completion.** A channel whose `progress` has reached `channelTicks` completes. With the default of 200, that is the 200th tick after the tick it started on. Completion sets `result` to the winner.
5. **Deadline.** If there is still no result and this is the deadline tick, any unfinished channel is cancelled (`deadline`) and the match ends with no winner. Completion runs first, so a claim completing on the deadline tick wins (§2).

When the match ends, by claim or by deadline, every encounter in the tick's input is reported as ending without theft (sorted by id), because match outcomes are frozen. `match-ended` comes last.

## Events

Each tick's events are listed in the order of the phases above:

| Event | Fields | The caller should |
| --- | --- | --- |
| `claim-interrupted` | `playerId`, `reason` (`duel`, `disconnected`, `ineligible`, `moved`, `released`, `deadline`), `progress` lost | Clear the claim UI or alarm |
| `protection-ended` | `playerId` | End that player's spawn or return protection |
| `claim-started` | `playerId` | Show the channel and warn nearby players |
| `claim-completed` | `playerId` | Commit the winner |
| `duel-ended-without-theft` | `encounterId`, `playerIds` | End the duel with no rubbing transfer |
| `match-ended` | `reason` (`claim` or `deadline`), `winner` or `null` | Freeze outcomes and show results |

Every event also carries `tick`. `replayClaim(config, state, inputs)` steps a list of ticks and returns the final state, every event and the final `hashState`.

## Tests

- `claim.test.ts`: scripted cases for each rule, with frozen inputs to prove the step does not mutate them.
- `determinism.test.ts`: 60 seeded random scripts. It checks that at most one winner is committed, that the state is frozen after the result, the per-tick invariants, and identical hashes on replay. The symmetry checks are reordered input, rotated and mirrored positions, order-preserving relabelling, and a 1 000-trial oracle for the closest-then-lowest-id rule under random relabelling.
- `packages/content/src/claim/claim.test.ts`: the constants and the validator.
# Architecture

The §14 browser architecture as far as the §3 sea, the §6 encounters at sea, §18 stage 2's collect, fight, steal and recover loop, and the §18 combat spike: browsers join a private match on one authoritative Colyseus room, the shared fixed-step simulation sails the ships over an authored tile map, and every browser draws what the server lets it see. A grapple that lands starts a 1v1 duel inside that room, fought with §15's prediction and rollback (the netcode is in `docs/duel.md`); the same duel also runs in a standalone duel room, for practice and private 1v1s. The objective ledger (`docs/objectives.md`) runs inside the room and is the only writer of rubbings and gold.

| Workspace | §14 component | What it holds now |
| --- | --- | --- |
| `apps/web` | Browser client and web shell | Landing page, HUD (with the island's types, the cache's contents and the hold's progress while moored), the purse beside the game (gold, rubbings, the last settlement, the winner's theft choice on keys 1 and 2), keyboard helm (E and J latched), input sender, snapshot interpolation, one Phaser game per page: the sea scene (tile map, following camera, ships, telegraphs, duel markers, cache chests, fogged minimap) and the arena scene; the duel client over a transport seam (keyboard with tap latch, `DuelClientSession` loop, duel HUD, dev-only latency setting) |
| `apps/server` | Match process | `MatchRoom` (one Colyseus room per match: the simulation, the encounter rules, its duels at sea and the objective ledger), the ledger's place on the sea (`objectives.ts`: source sites, E's target, the nearest dock by sea), the Schema mirror, per-client views, input gate, entry points; `DuelRoom`; `DuelMachine`, the duel both rooms run, and its input gate; the shared private admission |
| `packages/simulation` | Shared fixed-step functions | Integer match state, heading table, sailing, collisions, docking, stopping and returning ships, visibility rule, seeded generator, `hashState`; the encounter rules (`/encounters`, `docs/encounters.md`); the duel (`/duel`) and its netcode (`/netcode`: `DuelAuthority`, `DuelRollback`, `DuelClock`, `DuelClientSession`, the input-delay policy) |
| `packages/protocol` | Data contracts (§16) | Protocol version (6), create and join options, the input schemas and validation (buttons: interact, grapple), the duel messages (with `duel-ready` at sea), the theft choice (`choose-theft`), refusal messages, the test-only placement request and source layout |
| `packages/content` | Content and tuning (§17) | The slice sea (generated from Tiled), the Tiled converter, map validators, ship tuning, sight and engagement ranges, rules presets, frame budgets |
| `packages/test-tools` | Test harness (§17) | `HeadlessClient`: a browserless player on the real Colyseus SDK that also records the raw frames it receives, and fights at sea through its `fighter`; `HeadlessDuelClient` (the browser's `DuelClientSession` on the SDK, driven by a script, over a duel room or a match room), `ImpairmentProxy`, and `replayRecordedDuel` |

The HTTP service, PostgreSQL, static hosting and monitoring are not built yet (`infra/` is a placeholder).

## The sea

- **Map format and pipeline.** The map is `assets/source/maps/slice-sea.tmj`, in a documented subset of Tiled's JSON format (`packages/content/src/tiledMap.ts`): orthogonal, finite, 24 px tiles (`TILE_PIXELS`, as drawn); one imageless tileset whose tiles carry a `type` of `sea`, `land`, `shoal` or `dock`; a `terrain` layer as a plain gid array; an `objects` layer with a named `island` rectangle per island (property `theme`), a `spawn` point per slot (properties `slot` and `facing`), one `hub` point and a `final-socket` rectangle per hidden final-island socket (properties `claimX`, `claimY`). Nothing else is accepted. `npm run map:build -- --from-sketch` writes it from one mirrored ASCII quarter (`sliceSeaSketch.ts`; a unit test fails when they differ). `npm run map:build` (`scripts/build-map.ts`) converts it into `packages/content/src/maps/sliceSea.ts` (terrain rows and objects) if it passes the validators; a unit test fails when that module is stale (it reads the `.tmj` as a Vite `?raw` import).
- **Validators.** `validateSeaMap` checks §2 and §3: four small islands, each land tile inside one island rectangle, each island with a dock beside its land and open sea; shoals; eight spawn slots on open sea outside the islands' bounding box and pairwise beyond `ENGAGEMENT_RANGE_TILES` (6); every dock and slot reachable by sea; and, by eight-way shortest paths (no cut corners) at full speed: each island's nearest neighbour 20–40 s away, no dock-or-slot crossing over 90 s, a dock within 40 s of every slot. No empty stretches: every navigable tile is within the sight radius of land, a shoal or a dock (not the edge). Routes meet: closing the disc around the hub (open sea near the centre; radius half the sight radius, so ships in it see each other) lengthens or cuts every shortest path between docks of different islands. At most 112 tiles a side. The slice sea (111 × 111 tiles, midline shoal walls open only in the hub's disc): neighbours 26 s apart, longest crossing 39 s, water within 9.9 tiles of an obstacle, 90 % open sea.
- **Final-island sockets (§3, §5).** `map.finalSockets` holds four identical dockless islets (one sketched islet, mirrored), each a rectangle of at most 6 × 6 and a claim tile: open sea beside it whose centre is the claim point, the treasure circle's centre (`TREASURE_CIRCLE_RADIUS_TILES`). Their land belongs to no island, so docks, sailing, respawn and visibility treat them as plain land. `validateFinalSockets` (run by `validateSeaMap`) requires every claim tile within 90 s of every spawn slot, at least two sockets in any sector holding one (`sectorOf`: column ⌊3x / width⌋, row ⌊3y / height⌋, the grid a sector reveal must use), at least 12 navigable tiles in each circle, and nothing within 8 tiles of what the running tests sail on (`keepClearZones`: the hub, spawn slots, docks and 14 tiles out from each, the out-of-sight row). The slice's sockets sit two in the north-centre sector and two in the south-centre one. `chooseFinalSocket(map, secret)` picks a match's socket from a 32-bit secret the server draws from a cryptographic source, mixed by the murmur3 finaliser before the modulo; never pass the public match seed (§3). Nothing uses the choice yet.
- **Sailing.** Positions are integer sub-units (256 a tile); headings are 64 directions, 0 east, clockwise (y grows down), unit vectors from a literal cosine table. Each world step the throttle (`-moveY`) accelerates towards 39 sub-units a step (3.05 tiles a second), brakes, or reverses slowly from a stop; `moveX` turns a heading a step (3.2 s a circle); none coasts to a stop. On 24 px tiles that handles like the old five tiles a second on 16 px (unit tests hold it within 25 %). The hull is a square of half-size 80. A move sweeps each axis in turn through the tile columns or rows its leading edge enters and stops flush at the first land, shoal or map edge: a ship slides along an obstacle met at an angle, runs aground head-on, and never tunnels.
- **Docking.** Hold E near a dock to moor, at any speed and throttle: with the hull on or beside the berth tile (unless pinched), or within reach with a clear run, it moves to the dock's centre, stops and records the dock, so no arrival slides past or grounds beside it (pinched: a diagonal tile whose two shared tiles are blocked). It stays moored while E or the throttle it moored with (`mooredThrottle`) is held; pressing a throttle after releasing that one, or the other direction, casts off. An input stall does not: the server gives a lapsed client no input, keeping the latch. The keyboard keeps a tap of E until its next read (not past a blur), the server until its next step; then the HUD says "Press E to dock".
- **Visibility boundary (§16).** The room's `ships` map is tagged `.view()`. Each client gets a `StateView`; after every mirror the room puts into it the client's own ship and each ship within `SIGHT_RADIUS_TILES` (10, `visibleShipIds`) and takes out the rest, so Colyseus encodes no other ship into that client's patches (an integration test checks the decoded state and the raw frames). `players` in the state is the public player count. Terrain is static content every client bundles, never synced; the minimap fog is client-side presentation, not a security boundary.
- **Test placement.** Tests place ships through `POST /__test/place` (code, session id, tile, heading); its tile bounds come from the map. Only the dev and test entry (`apps/server/src/dev.ts`) offers it, when `PIRATE_SEA_RACE_TEST_PLACEMENT=1`; the production entry (`main.ts`) never reads that, which the build smoke test checks. It only moves a ship: admission and views are unchanged.
- **Test-only timings and source layout.** `startGameServer({ matchTuning })` gives every match of that server other rules (a short seat reservation, respawn wait or duel absence) or a pinned source layout; integration tests use it and assert in world ticks. Colyseus has one matchmaker per process, so each integration test file has one set of timings. The dev and test entry also reads `PIRATE_SEA_RACE_TEST_SOURCES` (for example `sun,sun|moon,moon|sun,sun|moon,moon`: the types of each island's sources), which the browser tests set so a scenario picks an island by type. `main.ts` reads neither (the build smoke test starts it with a malformed layout set) and turns the per-tick invariant checks off.

## Duels at sea (§6, §14)

- **Encounters in the room.** Each world step (20 Hz), after sailing, `MatchRoom` builds one tick's snapshot for `stepEncounters` (`docs/encounters.md`): every ship's position and heading, whether its player is connected, pressed J since the last world step (the input gate latches it like E), has a loaded arena, or started a collection or cache claim last tick (which ends protection). It passes back the reports of duels that ended since the last tick, and a settlement only once the ledger has settled the duel (below). It applies the events: `duel-reserved` stops both ships and opens a duel; `duel-started` starts its fight; a ready-check `duel-forfeited` or `duel-cancelled` ends it; `player-returned` and `player-respawned` move a ship (at rest, or moored at the dock). Everything else (attempts, protection, cooldowns, the loser's wait) is mirrored from the rules' state. The rules alone choose targets and decide hits, returns and docks; the room never re-implements them. Reserved and respawning ships get neutral input, so they stay put. Departure protection needs a match start, which private matches do not have yet, so no one starts protected.
- **One duel machine.** `DuelMachine` (`apps/server/src/duelMachine.ts`) is the duel both rooms run: seats and their `DuelInputGate`s, the 180-frame countdown with round-trip probes and the input delay chosen 30 frames before its end, `DuelAuthority` stepped at 60 Hz with a bundle every third frame, the reconnection bookkeeping (a dropped seat is marked away, a returning one gets a snapshot bundle) and the forfeits decided together at the next frame boundary. It writes a lobby schema and sends through a callback, so the host room owns clients and timers. `DuelRoom` starts the fight when the countdown ends (`start: "countdown"`); the match room starts it when the rules say so (`start: "called"`: the countdown is over and both fighters sent `duel-ready`). A countdown that ends with a fighter still loading waits in `waiting`, without probes; clients drop their session then, so the fight's clock starts from the fight's own frames. The match room keeps each duel's lobby for 2 s after settlement (`DUEL_RESULT_TICKS`), so both read the result.
- **Absence** (§12, on the world tick). A drop anywhere disconnects the player in the ledger at once; the ship stays in the world, grapplable, for the 60 s seat reservation. A fighter away from an unfinished duel for 10 s, counted in world ticks, forfeits it (both on one frame: no winner, reported as cancelled) and respawns as any loser, keeping the seat. Back before the deadline, the same player continues (`reconnectPlayer`; a fighter gets a snapshot bundle). Colyseus' `allowReconnection` is only an outer bound (70 s) that keeps the socket's slot: at the ledger's deadline the room expires the reservation and releases that slot; any other leave (consented, or the outer bound first) is a quit.
- **Message routing.** A duel's `duel-frames` and `duel-probe` go to its two fighters only, with `client.send`; the room routes `duel-input`, `duel-probe` echoes and `duel-ready` from a session to that session's duel and drops them from anyone else. In the browser, `SeaDuelRouter` listens for the duel messages once per match and hands them to the duel client of the moment (a message that beats the lobby's patch waits for it); the same `DuelClient` runs a standalone duel over `duelRoomTransport`.
- **Visibility (§16).** The state's new maps are filtered per client like `ships`: `grapples` (telegraphs, keyed by attacker: in a view when its attacker is in sight, or when it is the viewer's own or aimed at the viewer; each attempt has a twin entry with `defenderId` blank, which a viewer who sees the attacker but not the target gets instead), `markers` (a duel's position and reservation tick under an opaque key, nothing naming its fighters: in a view within the sight radius), `caches` (a recovery cache's position and dock, no contents: within the sight radius), `status` (a player's own mode, protection, cooldown, respawn tick, gold, rubbings, holds and theft choice: only the player's), `duels` (a duel's lobby: only its two fighters'). A ship in a duel or waiting to respawn is in no one else's view; its own player keeps it until it waits to respawn. A fighter or a player waiting to respawn sees no other ship, telegraph, marker or cache. Integration tests check the decoded state and the raw frames of a watcher in sight and a stranger out of it.
- **One game per page.** The match page's Phaser game (canvas renderer, see Rendering) holds the sea scene and the arena scene (`MatchGame`); a duel puts the sea to sleep and starts the arena with that duel's client, and its end wakes the sea (`data-scene` says which shows). The duel HUD moves beside the canvas meanwhile. The standalone duel page's game holds only the arena. The helm is read during a duel (so a J tapped in the arena is not kept) but the sea gets neutral input.

## Rubbings in the room (§4, §11, §12, `rubbings-theft`)

- **The ledger per match.** `MatchRoom` creates a `slice` ledger with the match, seeded from its own private randomness (`MatchTuning.random`: `node:crypto`'s `randomInt` in production, never the public match code; tests inject their own source through `startGameServer({ matchTuning })` and show the deal follows it, `tests/integration/ledgerSeed.test.ts`). Its sources stand at each regular island's docks (two per island, in dock id order), all unlocked until the ruins are wired (`objectives-endgame` will lock them). The ledger is the only writer of rubbings and gold: the room calls its operations and never moves either itself, and after every world tick it checks `checkLedger` and its own invariant (every player the ledger counts in the match has a ship, and every ship such a player) in development and tests.
- **Collecting and claiming.** Holding E moored at a dock is one gesture: E moors, and the same hold works on E's target there, the island's first sealed source of a type the player lacks, else a cached rubbing of a type they lack (fixed type order). The room continues the ledger's hold every held tick; releasing E, casting off, a reservation or a disconnect cancels it, and progress resets. Starting a hold ends protection on the next tick.
- **Settlement order.** Each world tick: `advanceLedger` (a closed choice window settles with the default); the §12 timers (duel absence, seat expiry into a cache at the respawn dock); `stepEncounters`, whose reports tell the ledger a fight's result and the rules its end, and tell the rules `settled` only once the ledger has settled the duel; then the holds. On a win with an eligible type the winner gets 5 s to send `choose-theft`; a draw, a cancellation or a win with nothing to take settles at once (gold still moves on a win). Only then do the players return. The fighters' lobby stays in their views through the choice. Both fighters' notices carry the settlement's tick, who picked the stolen type (`settledChoice`: the winner, or the default at the deadline) and the choice's deadline tick, so the purse says "You chose Moon" (the loser: "They chose Moon") or "Taken by default: Moon". The web client maps a key (1, 2) or a click on option *n* to a type in one pure function (`chosenTheftType`, `hud.ts`) before it sends `choose-theft`.
- **Messages.** `choose-theft` `{ duel, type }` (protocol v6): the opaque key of the sender's own duel lobby and a rubbing type, zod-validated, at most 64 bytes and 8 a second; the ledger accepts it only from the winner, inside the window, for an eligible type, and otherwise changes nothing. Collecting and claiming need no message: E is the input's interact button.
- **What each client sees (§16).** Gold, rubbings, the hold and its progress, the last results and the theft options are in the player's own `status` entry only. The island's sealed types and a cache's contents are filled in only while the player is moored at that island's dock or that cache's dock. A cache is a contentless marker at its dock, in a view within the sight radius. Integration tests check raw frames: an onlooker in sight of a collection and a duel never receives a rubbing type at all.
- **Leaving.** A reservation that expires removes the player and puts their remaining rubbings in one cache at the dock the encounter rules would respawn them at; a quit (or Colyseus' outer bound) forfeits a duel in progress and caches the rest at the dock nearest the ship by sea (`seaPathCosts`). No path removes a ship while the ledger still counts its player. A cache never despawns; claimed empty, it disappears.

## The duel (combat spike)

- **Duel room.** `DuelRoom` (room name `duel`) holds one duel, a `DuelMachine`: two players, or one in practice against a server-side dummy (player two, `idle` or `guard`). It is admitted like a match, by the same code in `admission.ts`: a one-time create token, `onAuth` before any seat, the room's own check, `filterBy(['code', 'createToken'])`, no token in the listing. The countdown (180 frames) starts once every seat is taken; the machine probes round trips during it, chooses the shared input delay 30 frames before the end, then steps `DuelAuthority` at 60 Hz, which the room's `setFixedTimestep` drives. Inputs go through `DuelInputGate`, which admits them through the same `InputAdmission` as the world's `InputGate` (the rate window and the protocol validation: 128 bytes, 60 a second of room ticks, increasing sequence, 30 frames of lead), so the two cannot drift, and counts its drops. Frame bundles and probes are Colyseus messages; the lobby is a small Schema state. A drop keeps the seat for 10 s (`allowReconnection`); leaving, or staying away, forfeits, decided at the next frame boundary (two forfeits on one frame: no winner). The rules and rates are in `docs/duel.md`.
- **One rollback core.** The browser's `DuelClient` and `HeadlessDuelClient` both run `DuelClientSession` from `@pirate-sea-race/simulation/netcode`; they differ only in transport and input (keyboard or script), and each plays over a duel room or a match room. The arena draws the predicted state; the HUD shows the confirmed one (server-equal health, stamina and clock) and the room's result. `window.__duel` exposes the session's counters and tagged inputs, read-only, for the browser tests.
- **Impairment harness.** `ImpairmentProxy` is a TCP proxy (Node's `net`, no new dependency) between a client and the server. It forwards HTTP untouched in content and splits the WebSocket stream into frames; each frame waits half the round trip plus a uniform ±jitter/2 in its direction, never overtaking the frame before it, and a lost frame (seeded draw) waits a further retransmission timeout (200 ms), stalling everything behind it as TCP does. `sever()` cuts every connection (optionally refusing new ones) for the reconnect tests. `tests/integration/duelHarness.test.ts` runs a scripted duel between two headless clients through it, with no impairment and at 80 ms, 20 ms jitter and 1 % loss (and `seaDuelHarness.test.ts` the same duel at sea, at 80 ms, 20 ms and 1 %, with the scripts and budget of `harness.ts`), and requires no desync at any of the ~180 hash checks per client, no rate-limited input, and corrections at most one per change of the opponent's applied input plus one per own substituted input, and at most 8 a second; it prints and annotates the counts. `replayRecordedDuel` replays a log (for example the pairs a client received) with `replayDuel`.
- **Dev latency.** Only in `npm run dev` (`import.meta.env.DEV`), `?rtt=80&jitter=20` on the page delays that browser's duel socket both ways, probes and pings included; the build smoke test checks the production bundle does not contain it. The browser checks run the production build, so the setting is tested below the browser: `apps/web/src/devLatency.ts` has no DOM dependency, unit tests with fake timers check its delay, jitter bound and order on a real SDK room, and `tests/integration/devLatency.test.ts` wraps two headless duel clients in it and checks that the room's measured round trip and chosen input delay rise above the same duel without it.

## Rules the code keeps

- **Purity.** `simulation`, `protocol` and `content` import no Phaser, Colyseus, DOM, timers, wall-clock time or `Math.random`, and call no floating-point transcendental `Math` function. Their tsconfig leaves out the DOM library, and `tests/unit/purity.test.ts` fails on a violation.
- **Integers.** Every number in the simulation state is an integer, so `hashState` (64-bit FNV-1a over a canonical serialization) does not depend on the JavaScript engine; a determinism test replays an input log.
- **One clock.** The room steps the simulation 60 times a second with Colyseus `setFixedTimestep`. World logic runs on frames divisible by 3 (20 Hz); the room then mirrors the plain state into its Schema and updates the views, and Colyseus patches clients at 20 Hz. Integration tests measure both rates, also with eight sailing ships in one cluster.
- **The server alone writes state.** At sea, clients send only `input` messages, `{seq, frame, buttons, moveX, moveY}`, validated with zod (the grapple is a button: the rules choose its target, never the client). `InputGate` drops, and counts, messages over the rate cap (60 per second of match time) or over 128 bytes, malformed ones (axes outside [-1, 1] are rejected, not clamped), ones whose sequence number is not higher than the last, and ones tagged more than 30 frames ahead. A held input lapses to neutral after 15 frames. An accepted world input applies from the server's next step whatever frame it names, since sea clients do not predict; a duel input applies to exactly the frame it names (`docs/duel.md`). Unknown message types are dropped. Colyseus's own limits sit above these: WebSocket frames over 4 KiB and more than 240 messages a second disconnect.
- **Joining.** Matches and duels share the admission code (`apps/server/src/admission.ts`). Colyseus serves `create`, `join`, `joinOrCreate` and `joinById` over HTTP and reserves a seat before any room check, so a private match is guarded in three layers. The static `onAuth` runs before any seat is reserved: it refuses a mismatched protocol version (426), a request with neither or both of `code` and `createToken` or a malformed token (400), an unknown code (404) and a full match (409). A `create` carries a one-time 128-bit `createToken`; the room is registered with `filterBy(['code', 'createToken'])` and `onCreate` replaces the listing's metadata with `{code, custom}`, so no listing holds a token and a token-carrying request can only create. The room's `onJoin` is the backstop, and the only check `joinById` meets after `onAuth`: one seat with the creator's token, then only seats with the match's code (404 for another code, 403 otherwise). Refusal messages stay under 100 bytes. A caller who knows a room id can still hold seats with `joinById` until each reservation expires (15 s).
- **Rendering.** The client draws the ships the server sent 100 ms in the past, interpolating between patches; the HUD lists their latest decoded state. The camera follows the player's ship over a Phaser tile map at 24 px a tile (the 480 px sight circle fits the 800 × 560 view) that leaves open sea to the background colour, keeping a software renderer fast. The sea does not predict; the duel arena does (above). Both of the page's Phaser games use the canvas renderer: the standalone duel page's arena, and the match page's one game holding the sea and the arena. With `Phaser.AUTO`, headless Chromium (the GPU-less case: WebGL in software, on the main thread) starved the duel client's 4 ms tick during a fight at sea: the `sea-duel` browser test, which records the `DuelClient`'s tick intervals through the fight and requires their 95th percentile under 16 ms, measured 135 ms. With `Phaser.CANVAS` it measured 8.5 ms (host) and 8.9 ms (guest), so the match game now uses the canvas renderer too.

## Toolchain

npm workspaces, TypeScript 7.0.2 (`tsc` for typechecks and package builds), Vite 8.3.0 (web build), Vitest 5.0.1 (`unit` and `integration` projects), tsx (map script and dev server), Phaser 4.2.1, `colyseus` 0.18.8 with `@colyseus/schema` 5.0.34, `@colyseus/sdk` 0.18.4, zod 4.6.5, Playwright 1.63.0. Workspace packages export a `@pirate-sea-race/source` condition that points at `src/`, so development and tests need no build. `npm run build` compiles each package to `dist/` in dependency order, then `scripts/smoke-build.ts` loads every workspace export from `dist/`, starts the built server on a free port, creates a match through the SDK, waits for the creator's ship and checks that no test-placement route answers, with every wait bounded. `colyseus` brings `uWebSockets.js` in from GitHub, so `npm ci` needs github.com as well as the npm registry. The duel added no dependency: `packages/test-tools` now also depends on the workspace's `@pirate-sea-race/simulation`, and the smoke test also loads `@pirate-sea-race/simulation/netcode` from `dist/`, checks the web bundle for the dev-only latency setting, and plays the first frames of a practice duel on the built server.
